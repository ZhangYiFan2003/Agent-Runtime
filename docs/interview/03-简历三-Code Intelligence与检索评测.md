# 简历三：Code Intelligence 与检索评测

> 本册讲代码索引、混合检索、结构上下文和可复现评测。Agent 执行质量闭环见第 5 册。

## 0. 简历原句

> 构建 Code Intelligence，基于 tree-sitter AST 分块与 SHA-256 增量索引，融合 FTS5 / BM25 与 Embedding 检索并通过 RRF 排序，结合符号解析与调用关系补充跨文件上下文；建立 lexical / vector / hybrid 固定离线检索集，以 Recall@5 / MRR 做检索回归。

## 1. 这条经历解决了什么问题

Coding Agent 的瓶颈常常不是模型不会写代码，而是没有把正确代码放进上下文。`grep` 对精确名称很好，却难以处理同义表达；纯向量检索能找语义相近内容，却可能错过函数名、异常码等强关键词；只返回命中片段又缺少定义、调用者和被调用者。

Axiom 把问题拆成索引、召回、融合、结构扩展和评测五段。AST 分块尽量保持函数/类的语义边界；文件 SHA-256 决定是否需要重建；词法、向量和符号通道分别召回；RRF 用名次而非不可比的原始分数融合；最后按调用关系补充有限上下文，并用固定数据集防止优化后悄悄回归。

## 2. 30～45 秒主回答

我做的 Code Intelligence 不是单纯接一个向量库。索引阶段用 tree-sitter 按函数、类等 AST 结构分块，文件内容用 SHA-256 做增量判断，并把 chunk、FTS5、embedding、符号和调用边写入 SQLite。查询阶段同时做 BM25 词法召回、向量召回和符号召回，再用 RRF 融合排名，最后补充定义、引用和有限深度调用关系。

效果用固定离线数据集的 Recall@5 和 MRR@5 验证。当前提交的 20 条 holdout 上，hybrid_v2 的 Recall@5 为 0.85、MRR@5 为 0.7667，但向量通道使用确定性离线 embedding，报告明确写着这不代表生产语义质量，也没有执行真实 embedding 基准。

## 3. 2～3 分钟完整故事

我先定义检索目标：不仅要“包含相同词”，还要支持自然语言描述定位代码，并给 Agent 足够的跨文件证据。分块时选择 AST，是因为函数和类比固定 500 token 更符合代码语义；语法错误或不支持的结构则回退到文件级/保守分块，保证索引不因一个文件失败而整体不可用。

增量不是 tree-sitter 的增量解析。当前做法是计算文件 SHA-256：文件未变化就复用索引，变化则重新解析该文件并替换其 chunks、symbols 和 references；调用图为了避免陈旧边会做更保守的重建。这一设计适合本地仓库，但不能说“修改一行只重新 embedding 一个 chunk”，因为当前更新粒度主要是文件。

召回阶段保留多个通道。FTS5/BM25 擅长精确标识符和词频；Embedding 处理语义改写；符号通道处理定义名称。原始 BM25 和余弦分数不在同一尺度，直接相加会依赖脆弱归一化，所以使用 Reciprocal Rank Fusion（RRF，倒数排名融合），按各通道名次贡献得分。之后 `CodeContextBuilder` 以命中项为种子，补充唯一符号定义、引用、调用者和被调用者，但受 item、深度、字符与估算 Token 上限约束。

评测中我会区分开发集、留出集和真实生产质量。当前 40 条 development 用于调权，20 条 holdout 验证泛化；另有 80 query 的版本对比工件。离线确定性向量让回归可复现，但不能证明真实 embedding 的语义表现。数字必须带数据集、commit、模式和限制一起说。

## 4. 架构与调用链

```text
Repository
  ↓ 文件发现 + SHA-256
tree-sitter AST → chunks / symbols / references
  ↓
SQLite schema v6：chunks + FTS5 + vectors + graph
  ↓ 查询
BM25 ─┐
Vector ├─ RRF 融合 → Top seeds → 定义/引用/调用关系扩展 → 有界 Context
Symbol ┘
  ↓
Agent / 离线 Recall@5、MRR@5 回归
```

## 6. 必须讲清的技术点

**Recall@5** 表示相关目标是否出现在前 5 个结果中，适合衡量“有没有召回”；**MRR@5** 对第一个相关结果的排名取倒数再平均，相关结果越靠前越高。二者不能替代最终 Agent 任务成功率。

**AST 分块** 保持语法结构，比固定窗口更容易保留完整函数；代价是跨语言规则、错误恢复和超大节点处理更复杂。

**RRF** 的典型形式是把每个通道中 `1/(k+rank)` 累加。它避免直接比较 BM25 与余弦分数，但会丢掉部分原始分差信息，也仍需调通道权重和候选规模。

**调用图** 是启发式、保守的静态近似，不是编译器级精确语义。Python 动态派发、Java 接口实现和 JS/TS 动态属性都可能造成误报或漏报。

## 7. 设计理由、替代方案与取舍

SQLite 适合单机、可复现、零运维索引；FTS5 可直接提供 BM25。当前向量按本地存储和线性扫描工作，仓库规模适中时简单可靠。百万 chunks 时才需要 ANN 向量索引、分片增量任务和独立检索服务。

为什么不是 grep？grep 是很好的强词法工具，但不能稳定处理语义改写和结构扩展。为什么不是纯 embedding？代码标识符、路径和错误码常靠精确匹配。为什么不是 LSP/编译器？它能提高类型与调用解析精度，但跨语言部署、构建环境和失败隔离更重。当前设计是在精度、可移植和本地运维之间取平衡。

## 8. 故障与边界场景

- 文件语法损坏：保守回退，记录解析状态，不让整个索引失败。
- embedding provider 失败：词法/符号仍可用；不能把缺失向量静默当成完整 hybrid。
- 模型或维度变化：用 embedding profile 区分，旧向量不能混用。
- 文件删除/重命名：清理旧 chunk、FTS、symbol/reference/edge，重命名通常表现为删旧增新。
- FTS5 不可用：降级到后备词法查询，性能和排序质量需单独观测。
- 调用图陈旧：跨文件解析后重建或失效，不能留下指向已删除符号的边。
- 结果相关但上下文超限：按预算和稳定排序裁剪，并保留原因标签，而不是无限扩图。

## 9. 分级面试题库（22 题）

### P0 — 简历直击题（10 题）

#### P0-1｜“为什么代码 RAG 要分块？直接把文件或固定 500 Token 切开不行吗？”

**面试官为什么问：** 简历第一处实现是 AST 分块。面试官想看你是否理解检索单元与代码结构的关系。

**先给结论：** 分块是为了让索引、召回和上下文预算都落在可管理单元上。固定窗口简单，但容易从函数中间切断；AST 分块更可能保留完整函数、类和符号边界。

**60～120 秒完整口语答案：** 整个文件作为一个向量时主题太多，命中后又会塞入大量无关内容；固定 500 Token 虽然语言无关，却可能把函数签名、实现和异常处理拆开。Axiom 用 tree-sitter 找函数、类等语法节点，生成带路径、行号和符号的 chunk，使精确检索和结构扩展都有稳定锚点。它也有缺点：多语言要维护规则，语法错误可能拿不到理想节点，超大函数仍可能过长，所以实现保留保守回退和预算裁剪，不能说 AST 分块永不丢语义。

**第一轮追问：**

- **追问：** “一个函数有一万行怎么办？”
  - **回答思路：** 保留父级语义，同时对超大节点二次切分并记录层级。
  - **30～60 秒可直接说出的答案：** “不能因为它是一个 AST 节点就整体塞入。理想方案是按内部语句块或 Token 上限二次切分，同时保留函数签名、路径和 parent symbol。当前 Axiom 没有通用的超大 AST 节点二次切分：索引可保留完整函数，最终由 Context Builder 的字符/Token 预算限制是否纳入，所以这是明确边界。”

**第二轮追问：** “语法错误怎么办？”——tree-sitter 能容忍部分错误节点，但若无法得到可靠结构，应退化到文件级/保守分块并记录状态，而不是让整个索引构建失败。

**常见坑：** “AST 一定比固定窗口好”；忽略超大节点、坏语法和跨语言成本。

**项目证据：** `src/axiom/rag/chunker.py`、`src/axiom/rag/parser.py`、AST tests。

#### P0-2｜“tree-sitter 是什么？为什么不用编译器或 LSP？”

**面试官为什么问：** 检查你对解析工具能力边界和工程选型的理解。

**先给结论：** tree-sitter 是面向多语言、可容错的增量解析库，适合快速得到语法树；它不是完整类型检查器。编译器/LSP 能提供更强语义，但依赖构建环境、classpath 和语言服务，部署更重。

**60～120 秒完整口语答案：** Axiom 需要在本地仓库中统一处理 Python、Java、JS/TS 等代码，首先要稳定拿到函数、类、调用表达式和导入等结构。tree-sitter 的语法树足以支持分块和启发式符号抽取，而且不要求项目完整编译。代价是它不知道真实类型绑定和动态派发，所以调用图只能做保守近似。若目标变成 IDE 级重命名或精确引用，应该接 LSP/编译器索引，而不是继续堆正则。

**第一轮追问：** “tree-sitter incremental parsing 和你的增量索引是一回事吗？”——不是。前者复用语法树编辑信息，当前 Axiom 主要用文件 SHA-256 判断是否重新解析和写索引。

**常见坑：** 把 tree-sitter 说成编译器；说用了 AST 就有准确类型和调用关系。

**项目证据：** `src/axiom/rag/parser.py`、`languages.py`、`symbols/`。

#### P0-3｜“SHA-256 怎么做增量索引？为什么不直接看 mtime？”

**面试官为什么问：** 简历直接写了 SHA-256 增量索引，面试官会问变化判断和实际更新粒度。

**先给结论：** 对文件内容计算 SHA-256，与索引中的指纹比较；相同就复用，变化就重建该文件相关记录。mtime 更便宜但可能因复制、检出、时钟或工具行为变化而误判，内容哈希更可靠。

**60～120 秒完整口语答案：** 更新时先发现工作区文件，对每个文件计算内容哈希并与存储记录比较。新增或变化文件重新解析、分块并更新 FTS、符号和向量；消失文件清理旧记录；之后再处理跨文件符号和调用关系。当前主要是文件级增量，所以修改一行可能重建这个文件的 chunks，并不等于只重算一个 chunk。哈希也有读取成本，但本地代码仓库中换来确定性和可复现性是合理的。

**第一轮追问：** “文件重命名怎么办？”——通常表现为旧路径删除、新路径新增；如果要保留历史身份，需要额外内容/符号匹配，当前不应夸大。

**第二轮追问：** “怎么避免新旧索引混在一起？”——同一文件替换应处于事务边界，删除旧关联记录后写新记录；跨文件图再重建或失效，失败要暴露为部分状态。

**常见坑：** 说“修改一行只 embedding 一行”；把 SHA-256 与 parser 增量解析混淆。

**项目证据：** `CodeIndex.update()`、`_sha256()`、`src/axiom/rag/store.py`。

#### P0-4｜“BM25 是什么？为什么它适合代码搜索？”

**面试官为什么问：** 简历点名 BM25，后端/搜索面试官通常会追倒排索引、TF、IDF 和长度归一化。

**先给结论：** BM25 是基于倒排索引的词法排序方法：词在当前文档出现更频繁会加分，跨文档越少见区分度越高，同时对词频饱和和文档长度做校正。函数名、类名、错误码等精确 token 很适合它。

**60～120 秒完整口语答案：** TF 表示查询词在当前 chunk 中出现情况，IDF 表示这个词在整个集合里有多稀有；`CheckpointConflictError` 这种少见标识符比 `get` 更有区分力。普通 TF-IDF 可能让重复词线性增益，也容易偏向长文档；BM25 用 `k1` 控制词频增益逐渐饱和，用 `b` 控制文档长度归一化。它的失败场景是同义改写、自然语言意图和词法完全不重合，所以不能单独替代 Embedding。

**第一轮追问：**

- **追问：** “`k1` 和 `b` 分别是什么？”
  - **回答思路：** 不背完整公式，解释调节作用。
  - **30～60 秒可直接说出的答案：** “`k1` 控制同一个词重复出现后，分数多快进入饱和；`b` 控制对文档长度差异的校正强度，0 接近不校正，1 更充分按长度归一。具体值不能凭经验宣称最优，要在固定数据集上调。”

**第二轮追问：** “BM25 为什么找不到‘防旧写覆盖’？”——如果代码只出现 CAS 或 conflict 等词，查询与文档词法不重合，Embedding 或查询改写更有机会召回。

**常见坑：** 把 BM25 说成语义模型；说词出现越多分数永远线性增长。

**项目证据：** `src/axiom/rag/store.py` 的 FTS5、`src/axiom/rag/ranking.py`。

#### P0-5｜“Embedding 检索从 query 到结果的完整链路是什么？”

**面试官为什么问：** 检查你是否只会说“转向量”，以及是否理解模型身份、相似度和失败模式。

**先给结论：** 索引时把 chunk 的代码与元数据文本编码成向量并持久化；查询时用同一 embedding profile 编码 query，计算相似度并取 Top-K。模型、维度或预处理变化时不能混用旧向量。

**60～120 秒完整口语答案：** Axiom 为每个 chunk 构造稳定 embedding 输入，调用 provider 得到向量并记录 profile。查询使用相同 profile 产生 query vector，当前本地路径计算余弦相似度后排名。余弦更关注方向而非向量长度，适合许多语义 embedding；如果模型已做单位归一化，点积也可能等价。Embedding 能处理语义改写，但会在罕见标识符、版本号和相近但无关代码上失败，所以必须与词法和符号通道互补。

**第一轮追问：** “为什么不用欧氏距离？”——取决于模型训练和归一化；余弦忽略长度，欧氏保留绝对距离。不能脱离 embedding 模型约定宣称一种永远更好。

**第二轮追问：** “Embedding 模型换了怎么办？”——profile 变化后重新生成对应向量，查询不能拿新模型向量和旧模型空间直接比较。

**常见坑：** “向量相似就一定业务相关”；忽略相同模型/维度/预处理要求。

**项目证据：** `src/axiom/rag/embeddings.py`、`vectors.py`、`CodeIndex.sync_embeddings()`。

#### P0-6｜“BM25 和向量分别解决什么？两路分数怎么合？”

**面试官为什么问：** 这是简历中 hybrid 与 RRF 最自然的主问题。

**先给结论：** BM25 负责精确词法，Embedding 负责语义，Symbol 再增强代码定义；原始分数尺度不可比，所以 Axiom 用 RRF 按排名融合，而不是直接相加。

**60～120 秒完整口语答案：** 例如搜具体函数名，BM25 和 Symbol 很强；用自然语言描述“控制旧状态覆盖”，向量可能更强。如果直接把 BM25 score 与 cosine 相加，一个可能是负值或无上界，另一个通常在有限区间，归一化稍变就会让某路支配。RRF 对每路第 `rank` 名贡献 `1/(k+rank)`，再按通道权重累计，关注多路是否把结果排在前面。`k` 越大，相邻名次差异越平缓；它简单稳健，但会丢失原始分差，权重仍要用开发集调。

**第一轮追问：**

- **追问：** “BM25 和 Vector 给出完全不同结果怎么办？”
  - **回答思路：** 不是人工选边，而是融合、保留来源和离线分类评测。
  - **30～60 秒可直接说出的答案：** “先让 RRF 按排名和权重融合，并保留每个候选的来源。再按 query 类型分析：符号型更信词法，语义改写更依赖向量。如果长期冲突，应该用开发集调权或做 query-aware routing，而不是看个例手调。”

**第二轮追问：** “为什么没有 Cross Encoder？”——当前本地范围先用低运维、确定性融合；reranker 会增加模型延迟和成本，只有候选召回已足够而排序仍是瓶颈时再加在召回之后、Context Builder 之前。

**常见坑：** “hybrid 一定优于所有单路”；“RRF 不需要调参与评测”。

**项目证据：** `src/axiom/rag/hybrid.py`、`CodeIndex._search_hybrid_v2()`。

#### P0-7｜“为什么还需要 Symbol、Definition、Reference、Caller、Callee？”

**面试官为什么问：** 简历提到符号解析和调用关系，面试官会问它们比 Top-K 文本多了什么。

**先给结论：** 文本召回告诉我们“哪段像答案”，符号和调用关系告诉我们“定义在哪里、谁使用它、它又调用谁”，用于补齐跨文件执行上下文。

**60～120 秒完整口语答案：** Definition 是符号声明/定义位置，Reference 是名称使用，Caller/Callee 是更具体的调用边。命中 `ToolExecutor.execute_all` 后，Agent 可能还需要 Tool 元数据定义、上层调用者和被调用的审批函数。Axiom 从命中 seed 出发补唯一符号、直接引用和有限调用路径，每项带 reason、距离和稳定顺序。静态解析受动态派发、重载和不完整类型信息影响，所以这些是辅助证据，不应覆盖强检索结果或被称为精确程序分析。

**第一轮追问：** “Python 动态调用怎么办？”——静态阶段只能保守处理或不连边；可引入类型信息、运行时 Trace 或置信度，但不能假装知道反射和 monkey patch 的真实目标。

**常见坑：** 把 reference 等同于 call；把静态图说成 100% 准确。

**项目证据：** `src/axiom/rag/symbols/`、`src/axiom/rag/call_graph.py`。

#### P0-8｜“Top-K 命中以后为什么不能全塞 Prompt？怎么防结构扩展爆炸？”

**面试官为什么问：** 检查检索与最终上下文是否真正闭环。

**先给结论：** Top-K 仍可能重复、超长或沿调用图指数扩张；Context Builder 必须按相关性和结构价值去重，并受条目、深度、字符和估算 Token 硬上限约束。

**60～120 秒完整口语答案：** 一个 seed 可能指向多个 definition、几十个 caller 和递归环。如果全部展开，检索命中了正确代码也会被无关上下文淹没。Axiom 对候选稳定去重排序，只扩有限深度的直接关系，记录 graph distance 和 reason，并在预算内选择最有价值项。预算耗尽时截断扩展而不是突破模型窗口；这能证明结构和资源边界，但最终是否提升任务成功仍要端到端 Eval。

**第一轮追问：** “为什么不是只取搜索前五？”——前五片段可能缺定义与调用背景；结构扩展补的是关系证据，但必须有预算。

**常见坑：** 把完整仓库或完整调用图塞给模型；认为更多上下文永远更好。

**项目证据：** `src/axiom/rag/context.py:CodeContextBuilder`、`tests/test_code_context.py`。

#### P0-9｜“你的 Golden Dataset 和 Ground Truth 是怎么做的？”

**面试官为什么问：** 看到 Recall@5/MRR，面试官自然会检查查询和相关答案由谁定义。

**先给结论：** Golden Dataset 是固定查询及其人工/规则审核的相关目标集合；Ground Truth 不是模型临时判断，而是版本化保存的期望文件、符号或 chunk。一个 query 可以有多个正确目标。

**60～120 秒完整口语答案：** 查询应覆盖符号精确查找、自然语言改写、调用/上下文问题和纯词法问题，不能只从代码复制函数名，否则会偏向 BM25。标注 relevant target 时要说明粒度：文件、符号还是 chunk；若多个实现都能回答，就应允许多个相关项。Axiom 将 development 和 holdout 分开，固定评测脚本和源 commit。当前数据规模仍小，主要用于仓库内可复现回归，不声称代表所有语言和真实用户分布。

**第一轮追问：** “holdout 能不能反复调参数？”——不能。反复查看并据此调权会把它变成开发集；应冻结，必要时另建新留出集。

**第二轮追问：** “Ground Truth 会不会过期？”——代码变更后要版本化数据集并审核目标，报告必须记录 source commit。

**常见坑：** 用生成 query 的同一模型自动标答案后直接称 gold；只收集系统能答对的问题。

**项目证据：** `benchmarks/retrieval/development-dataset.json`、`holdout-dataset.json`、结果工件。

#### P0-10｜“Recall@5 和 MRR 分别衡量什么？为什么选 5？”

**面试官为什么问：** 简历直接给出指标，必须能解释含义、选择和盲区。

**先给结论：** Recall@5 看相关目标有多少被前五覆盖；MRR@5 看第一个相关结果排得多靠前。选择 5 是当前上下文候选预算与评测约定，不是理论最优常数。

**60～120 秒完整口语答案：** 若每个 query 只有一个 relevant target，Recall@5 常退化为 Hit@5；有多个相关目标时，Recall 会看覆盖比例，而 Hit 只看是否至少命中一个。MRR 对第一个相关结果取倒数，第一名是 1、第二名是 0.5，适合关注“正确证据是否尽早出现”。Precision@K 在相关答案稀疏、标注不完整时容易把未标但有用片段当错；nDCG 在有多级相关性、需要评估整个排序时更合适。最终 K 应结合 Context 预算和任务效果验证。

**第一轮追问：** “Recall 高、MRR 低说明什么？”——能找到但排位靠后，正确证据容易在 Context 裁剪中丢失。

**常见坑：** 把 Recall@5 解释成“前五准确率”；把 MRR 当所有相关结果平均排名。

**项目证据：** `benchmarks/retrieval/evaluation.py`、retrieval result reports。

### P1 — 回答后的自然深挖（8 题）

#### P1-1｜“BM25 的倒排索引怎么工作？”

**为什么会被追到这里：** 你在 P0 解释了 BM25。

**30～60 秒回答：** 建索引时从 token 建立“词 → 出现在哪些文档/chunk”的 posting list，并保存词频、文档长度等统计；查询只访问相关 posting，而不是扫描全部文本，再用 BM25 排序。

**典型继续追问：** “SQLite 用什么索引？” **回答思路：** FTS5 维护全文倒排结构，普通结构化字段另由 SQLite B-tree 索引。**项目边界：** Axiom 调用 FTS5/BM25，不声称自己从零实现搜索引擎。

#### P1-2｜“语法错误或不支持语言时会怎样？”

**为什么会被追到这里：** 你说 AST 解析有回退。

**30～60 秒回答：** 单文件解析失败不能让全仓索引失败；保留文件级/文本回退和明确状态。质量会下降，但仍可被词法检索发现。

**典型继续追问：** “静默回退好吗？” **回答思路：** 不好，应记录解析覆盖率和失败文件。**项目边界：** 多语言支持以实际 grammar 和测试为准。

#### P1-3｜“Embedding 失败，hybrid 还能查吗？”

**为什么会被追到这里：** 你提到多通道互补。

**30～60 秒回答：** 可以显式降级 lexical/symbol，并在结果元数据中标出通道缺失；不能把降级结果仍宣称为完整 hybrid。后台可重试同步向量，但写入要按 profile 保持一致。

**典型继续追问：** “旧向量能继续用吗？” **回答思路：** 仅在 profile 相同且内容哈希一致时。**项目边界：** 当前不是高可用向量集群。

#### P1-4｜“为什么不加 Cross Encoder Reranker？”

**为什么会被追到这里：** 你说 RRF 只按名次，可能损失精细语义。

**30～60 秒回答：** reranker 能对 query-candidate 成对打分，提高前几名精度，但增加模型调用、延迟和部署成本。当前先保证多路 candidate recall 和可复现回归；若错误分析显示主要是排序而非召回，再放在融合后、Context 组装前。

**典型继续追问：** “候选多少？” **回答思路：** 由延迟预算和召回曲线决定，不拍固定数。**项目边界：** 当前未实现 learned reranker。

#### P1-5｜“多路检索权重怎么调？”

**为什么会被追到这里：** 你解释了 weighted RRF。

**30～60 秒回答：** 只在 development split 上做有限搜索，目标同时看 Recall、MRR、分类退化和延迟；选定后冻结，在 holdout 一次验证。不要看 holdout 结果反复改权重。

**典型继续追问：** “每种 query 一个权重？” **回答思路：** 可做 query-aware routing，但先评测分类器错误和复杂度。**项目边界：** 当前使用固定 v2 weights。

#### P1-6｜“Precision@K、nDCG 为什么不是主指标？”

**为什么会被追到这里：** 你解释了 Recall/MRR 的选择。

**30～60 秒回答：** 当前目标首先是让关键目标进入有限上下文并尽量靠前，且标注相关项可能不完整，所以 Recall/MRR 更直接。若有完整多级相关性标注，需要评价整个排序质量，nDCG 会更合适。

**典型继续追问：** “指标越多越好吗？” **回答思路：** 不是，选与产品决策一致且可稳定标注的指标。**项目边界：** 当前固定报告以 Recall/MRR 为主。

#### P1-7｜“离线检索高，为什么 Agent 仍会失败？”

**为什么会被追到这里：** 你主动承认检索指标只是代理指标。

**30～60 秒回答：** 正确 chunk 进前五不代表最终 Context 没被裁掉，也不代表模型理解正确、Tool 执行成功或修改通过测试。需要把检索版本接入固定 Agent 任务，多 trial 比较最终成功、Token、步骤和 cost per success。

**典型继续追问：** “怎么归因是检索导致？” **回答思路：** 固定其他变量，记录 retrieval/context fingerprint 与召回证据。**项目边界：** 当前有检索回归和 Agent Eval 基础，但不是完整因果实验平台。

#### P1-8｜“数据只有几十条，结果可信吗？”

**为什么会被追到这里：** 你报出了 development 40、holdout 20。

**30～60 秒回答：** 它足以发现仓库内明确回归和验证管线，却不足以估计广泛生产分布。要报告样本数、分类结果和置信边界，不把百分点当普适收益；后续从真实 Badcase 扩充多仓库数据。

**典型继续追问：** “为什么还值得做？” **回答思路：** 小而固定的数据集比主观 demo 强，能成为持续迭代起点。**项目边界：** 当前结论严格限于固定工件。

### P2 — 攻击、边界与架构取舍（4 题）

#### P2-1｜“你这个 deterministic embedding 能证明语义检索好吗？”

**最安全的结论：** 不能证明生产语义质量，只能证明向量通道、融合、评测与回归管线可确定复现。

**回答主线：** 报告已明确 real embedding benchmark 未执行；真实模型需重新建立数据、延迟、隐私和成本证据。

**不要说什么：** “holdout 0.85 就是线上真实召回率。”

**如果继续扩展怎么做：** 固定真实 embedding 模型与版本，扩展多仓库 holdout，并做任务级 A/B。

#### P2-2｜“用了 tree-sitter，你的调用图为什么还会错？”

**最安全的结论：** AST 给语法，不给完整运行时绑定。

**回答主线：** Python 动态调用、Java 接口派发、JS 属性和反射都可能不确定；当前图用于扩展候选，并以深度/预算限制风险。

**不要说什么：** “调用节点存在就能准确解析目标。”

**如果继续扩展怎么做：** 接类型/LSP/编译器索引，记录置信度，并用运行时 Trace 补充。

#### P2-3｜“为什么不用专用向量数据库或 Elasticsearch？”

**最安全的结论：** 当前本地仓库规模和零运维目标下 SQLite/FTS5 更匹配，不代表它无限扩展。

**回答主线：** 先看 chunks、QPS、更新率和 P99；线性向量或单机写成为瓶颈时再引入 ANN/独立检索服务。

**不要说什么：** “SQLite 和分布式搜索性能一样”或“上 Milvus 就自动提升质量”。

**如果继续扩展怎么做：** 版本化索引、后台构建、ANN、双读验证和原子切换。

#### P2-4｜“holdout 结果很好，能不能继续用它调到更高？”

**最安全的结论：** 不能；那会造成测试集泄漏。

**回答主线：** holdout 用于最终验证，观察后若要继续研发，应新增开发数据并最终换一批未见留出集。

**不要说什么：** “只调一点不算泄漏。”

**如果继续扩展怎么做：** 版本化数据切分、冻结评测流程、盲测和真实 Badcase 回流。

## 10. 重点追问树（7 条）

### 追问树 1：AST 分块

```text
代码 RAG 为什么要分块，为什么按 AST？
└─ 一个函数超过 Context 上限怎么办？
   └─ parser 遇到坏语法怎么办？
      └─ tree-sitter 为什么不换 LSP/编译器？
```

- **“超大函数怎么办？”**
  - **面试官意图：** 检查 AST 边界是否被机械当成不可分单元。
  - **回答思路：** 父级语义保留，内部再按语句块/Token 切分，携带 parent symbol。
  - **30～60 秒口述：** “AST chunk 的目标是保留语义边界，但一万行函数不能整体入模。合理演进是内部二次切分并保留函数签名和 parent symbol；当前实现尚无通用 intra-node splitter，可能索引完整函数，Context Builder 再按字符/Token 预算选择或截断，所以我不会说超大函数已被完美解决。”
- **“坏语法怎么办？”**
  - **面试官意图：** 追问鲁棒性与降级可观测性。
  - **回答思路：** tree-sitter 可容忍部分 ERROR 节点；失败时文件/文本回退，不拖垮全仓索引。
  - **30～60 秒口述：** “单文件语法错误不能让整个仓库不可搜。能提取可靠节点就继续，不能则降级到保守文本/文件分块，并记录失败文件和解析覆盖率。降级后结构质量下降，但 lexical 仍能召回，不能静默宣称 AST 全覆盖。”
- **“为什么不是 LSP/编译器？”**
  - **面试官意图：** 检查多语言、部署成本与语义精度取舍。
  - **回答思路：** tree-sitter 无需可编译环境、跨语言快；LSP/编译器更准但依赖重。
  - **30～60 秒口述：** “Axiom 首先需要函数、类、调用表达式等语法结构，并希望仓库不完整时也能索引，tree-sitter 更轻。LSP/编译器适合精确类型绑定、重命名和引用，但需要语言服务、classpath 或构建环境。当前调用图因此只是启发式证据，不是编译器真相。”

### 追问树 2：增量索引

```text
SHA-256 增量索引怎么工作？
└─ 为什么不用 mtime？
   └─ 修改一行到底重做多少？
      └─ delete / rename / embedding model 变化怎么办？
```

- **“为什么不用 mtime？”**
  - **面试官意图：** 判断内容哈希是否有必要。
  - **回答思路：** mtime 便宜但受 checkout/copy/时钟影响；哈希读取更贵但内容确定。
  - **30～60 秒口述：** “mtime 能做快速提示，但同内容复制会误报变化，某些工具又可能保留时间导致漏报。SHA-256 直接绑定内容，使本地回归可复现。代价是要读文件，当前仓库规模下可接受；更大规模可先用大小/mtime 筛选，再用哈希确认。”
- **“修改一行重做多少？”**
  - **面试官意图：** 捕捉‘增量到 chunk’的过度表述。
  - **回答思路：** 当前主要文件级：重解析该文件并替换 chunks/symbols/vectors，跨文件图更保守刷新。
  - **30～60 秒口述：** “当前不是 tree-sitter edit 增量，也不承诺只重算那一行。文件 hash 变化后主要重建该文件的 chunk、FTS、symbol 和 embedding 记录；跨文件引用/调用边为避免陈旧会更保守处理。这是文件级增量。”
- **“删除、重命名、模型变化呢？”**
  - **面试官意图：** 检查索引一致性和向量空间版本。
  - **回答思路：** 删除清旧记录；rename 通常删旧增新；embedding profile 变化重建且不混空间。
  - **30～60 秒口述：** “消失路径要删除旧 chunks、FTS、symbols 和边；rename 当前通常表现为旧删新增，不宣称保留历史身份。同一文件替换应在事务边界完成。Embedding 模型、维度或预处理变化会形成新 profile，旧向量不能和新 query 直接比较。”

### 追问树 3：BM25

```text
BM25 到底是什么？
└─ 倒排索引、TF、IDF 分别做什么？
   └─ k1、b 与文档长度为什么重要？
      └─ 为什么特别适合代码标识符？
```

- **“倒排、TF、IDF 是什么？”**
  - **面试官意图：** 检查是否只背‘BM25 适合精确词’。
  - **回答思路：** posting 定位候选；TF 表示当前 chunk 出现；IDF 表示全库稀有度。
  - **30～60 秒口述：** “倒排索引从 token 映射到出现它的 chunk，不用全表扫描。TF 表示查询词在当前 chunk 的出现强度；IDF 降低全库常见词权重、提高稀有词区分度。因此 `CheckpointConflictError` 比 `get` 更能锁定代码位置。”
- **“k1、b 和长度呢？”**
  - **面试官意图：** 追问 BM25 相对普通 TF-IDF 的关键。
  - **回答思路：** k1 控制词频饱和，b 控制长度归一；长文件自然含词多，不应无条件占优。
  - **30～60 秒口述：** “同一个词重复十次不应比一次线性高十倍，`k1` 控制增益何时饱和；长 chunk 更容易偶然包含查询词，`b` 控制按平均长度校正，0 近似不校正，1 更充分校正。这是 BM25 原理；当前 Axiom 使用 SQLite FTS5 的 `bm25()`，没有暴露项目级 `k1/b` 调参，实际调的是字段/融合权重。”
- **“为什么适合代码？”**
  - **面试官意图：** 把搜索原理落回简历场景。
  - **回答思路：** 类名、函数名、错误码、配置键是高信息稀有 token；同义自然语言是盲区。
  - **30～60 秒口述：** “代码查询经常直接带 `RunStatus`、函数名、异常码或配置键，这些 token 稀有且精确，BM25 很强。但‘防止旧写覆盖’与代码中的 `CAS` 可能没有词法重合，所以还要 Embedding；动态定义关系则由 Symbol 通道补。”

```text
query 和 chunk 怎么变成向量？
└─ cosine similarity 是什么？
   └─ Vector 为什么不能替代 BM25？
      └─ 当前 deterministic embedding 能证明什么？
```

- **“余弦相似度是什么？”**
  - **面试官意图：** 检查向量检索基础。
  - **回答思路：** 比较夹角方向，弱化模长；距离选择遵循模型训练/归一化。
  - **30～60 秒口述：** “索引和查询必须用同一 embedding profile。余弦是点积除以两个向量模长，关注方向是否接近；若模型已单位归一化，点积排序可能等价。它不是业务正确率，距离函数要服从 embedding 模型约定。”
- **“为什么不能 vector-only？”**
  - **面试官意图：** 追问 semantic retrieval 失败模式。
  - **回答思路：** 稀有标识符、版本、数字、相近但无关实现；BM25/Symbol 提供精确锚点。
  - **30～60 秒口述：** “向量擅长自然语言改写，但可能把语义相似却不是目标的代码排高，也可能弱化错误码、版本号和罕见函数名。代码场景同时需要精确身份与语义，因此保留 lexical、vector、symbol 三路比纯向量稳。”
- **“deterministic embedding 证明什么？”**
  - **面试官意图：** 捕捉最危险的效果夸大。
  - **回答思路：** 只证明管线、融合和回归可复现，不证明真实模型语义质量。
  - **30～60 秒口述：** “当前离线确定性向量让同一 commit 得到稳定结果，适合测试索引、候选和 RRF；它不代表生产 embedding 的语义召回。真实模型还要固定版本、重新建向量、测多仓库质量、延迟、隐私和成本。”

### 追问树 5：Hybrid/RRF

```text
BM25、Vector、Symbol 为什么要融合？
└─ 为什么不直接把原始分数相加？
   └─ RRF 公式、k、weight 是什么？
      └─ candidate size 与 reranker 放哪里？
```

- **“为什么不直接加分？”**
  - **面试官意图：** 检查异构 score 的尺度问题。
  - **回答思路：** BM25、cosine、symbol 分数分布不可比，归一化易漂移；RRF 用 rank。
  - **30～60 秒口述：** “BM25 可能无上界，cosine 常在有限区间，symbol 又是另一种打分，直接相加会让某路因尺度占优。RRF 只看各路名次，降低归一化敏感性；代价是丢掉原始分差，所以仍需数据集验证。”
- **“RRF 参数怎么理解？”**
  - **面试官意图：** 验证不只是会说融合名。
  - **回答思路：** 每路贡献 `weight/(k+rank)`；k 越大名次差越平缓；权重只在 dev 调。
  - **30～60 秒口述：** “候选在每一路按 rank 贡献 `weight/(k+rank)`，多路靠前会累计。`k` 大时第一和第五差距被压平，小则更强调头部；weight 表达通道先验。Axiom 在 development 调有限参数，再冻结到 holdout，不能看 holdout 反复调。”
- **“candidate 和 reranker 呢？”**
  - **面试官意图：** 追到两阶段检索取舍。
  - **回答思路：** 候选数由召回曲线/延迟决定；reranker 位于融合后、Context Builder 前。
  - **30～60 秒口述：** “每路候选太少会漏召回，太多增加融合和上下文噪声，应看 Recall@K 与延迟曲线。若错误分析说明召回够但头部排序差，可在 RRF 后、Context 组装前加 cross-encoder reranker；当前没有实现，不能当成现有能力。”

### 追问树 6：结构检索

```text
为什么 Top-K chunk 不够？
└─ definition / reference / caller / callee 有何区别？
   └─ 动态语言调用图为什么会错？
      └─ 图扩展如何避免 Context 爆炸？
```

- **“四类关系怎么分？”**
  - **面试官意图：** 验证结构检索语义。
  - **回答思路：** definition 是声明，reference 是使用，caller/callee 是调用方向；reference 不都等于 call。
  - **30～60 秒口述：** “命中调用点后，Agent 常要看被调定义和上层调用者。Definition 是符号定义，Reference 是名称使用，Caller/Callee 是更具体的调用边；一次赋值引用不是函数调用。Axiom 用它们补候选证据，不用静态图覆盖强文本命中。”
- **“动态语言为何会错？”**
  - **面试官意图：** 检查 AST 与运行时绑定边界。
  - **回答思路：** 反射、monkey patch、属性动态派发、接口/重载；保守近似或缺边。
  - **30～60 秒口述：** “AST 看见 `obj.run()`，但未必知道 `obj` 的运行时类型；反射和 monkey patch 更难。Java 接口派发、JS 动态属性也类似。当前图只做启发式扩展，可漏边或错边；精度要求更高要接类型/LSP/编译器或运行时 Trace。”
- **“怎么防图扩展爆炸？”**
  - **面试官意图：** 把结构检索连接到 Context Budget。
  - **回答思路：** 稳定去重、有限深度、item/字符/Token 上限、记录 reason/distance。
  - **30～60 秒口述：** “调用图可能有环和高出度，不能递归全展开。Axiom 从 Top seed 出发，只补有限深度的高价值关系，按稳定身份去重，并受条目、字符和估算 Token 硬上限约束；每项保留来源原因，预算耗尽就停止扩展。”

### 追问树 7：检索评测

```text
Ground Truth 到底怎么标？
└─ 多个相关 chunk、hard negative 怎么处理？
   └─ Hit/Recall/Precision/MRR/nDCG 各回答什么？
      └─ 只有几十条、Recall 高，凭什么相信 Agent 会更好？
```

- **“相关项和 hard negative 怎么标？”**
  - **面试官意图：** 检查 golden dataset 是否偏向当前系统。
  - **回答思路：** query 来自真实意图类型；标注粒度明确；允许多个 relevant；加入词相似但答非所问的难负例。
  - **30～60 秒口述：** “不能只复制函数名生成 query，否则天然偏 BM25。要覆盖精确符号、自然语言、调用关系和错误定位；Ground Truth 明确是文件、symbol 还是 chunk，一个问题可有多个 relevant。Hard negative 是词或语义很像但不能回答的代码；当前固定集没有单独的 hard-negative 标注字段，主要通过真实候选中的混淆项暴露问题。”
- **“这些指标怎么分？”**
  - **面试官意图：** 验证指标选择与标注假设。
  - **回答思路：** Hit 至少一个；Recall 覆盖比例；Precision 结果纯度；MRR 首个相关排名；nDCG 多级全排序。
  - **30～60 秒口述：** “Hit@K 只问前 K 是否至少有一个正确；Recall@K 问所有相关项覆盖多少；Precision@K 问返回项里正确占比；MRR 看第一个 relevant 排第几；nDCG 适合多级相关性和整个头部排序。当前目标是关键证据进有限 Context 且尽量靠前，所以主看 Recall@5/MRR@5。”
- **“几十条、Recall 高就够吗？”**
  - **面试官意图：** 追问统计可信度和代理指标盲区。
  - **回答思路：** 小集只作仓库回归；报告 dev40/holdout20 与 deterministic 条件；最终仍需任务级评测。
  - **30～60 秒口述：** “20 条 holdout 的 0.85/0.7667 能证明这份固定工件上没有回归，不能外推所有仓库。Recall 高也不保证 Context 没裁剪、模型理解正确或修改通过测试。下一层应固定其他变量，用真实 embedding 和 Agent task success、步骤、Token、cost per success 验证，同时防止反复调 holdout 造成泄漏。”

## 11. 面试官攻击面与防守口径

1. **“AST 就代表精确语义？”** 明确语法树与类型/LSP 边界。
2. **“增量到 chunk 级？”** 明确当前主要文件级。
3. **“BM25 公式会不会？”** 能解释 TF/IDF、饱和和长度归一化，不必机械推导。
4. **“RRF 一定更好？”** 用固定 split 证据回答，承认排序信息损失。
5. **“调用图 100% 准？”** 明确动态派发和保守近似。
6. **“0.85 是线上指标？”** 明确 20 条 holdout 和确定性离线向量条件。
7. **“数据太小没意义？”** 定位为可复现回归起点，不做泛化承诺。
8. **“检索高就代表 Agent 好？”** 继续看 Context 和任务级成功/成本。

## 12. 当前边界

### 【当前已实现】

tree-sitter 多语言解析与回退、AST chunks、SHA-256 文件级增量、SQLite schema v6、FTS5/BM25、可插拔 embedding、词法/向量/符号融合、RRF、符号/引用/调用关系、有界 Context Builder、固定 development/holdout 离线评测。

### 【当前部分支持】

调用图是启发式静态近似；本地向量路径适合中小仓库；离线确定性向量验证管线而非生产语义质量；检索指标尚不能单独证明 Agent 完成率。

### 【未来可扩展】

真实 embedding 多仓库基准、ANN 索引、版本化后台构建、LSP/编译器语义、租户隔离索引、在线坏例回流、检索质量与任务成功/成本联合门禁。
