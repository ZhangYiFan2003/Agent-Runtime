# Axiom 面试前 30 分钟速查表

> 只在最后一轮复习使用。细节回到第 1～6 册，生产场景回到第 8 册。

## 1. 30 秒项目介绍

Axiom 是一个面向本地和企业内部 Coding Agent / Tool 工作流的 Durable Agent Runtime。它把 ReAct、Plan-and-Execute 和 Planner/Worker/Reviewer 统一到可恢复 Run 上，并围绕 Tool 安全、Context、预算、无进展、依赖超时与安全重试、完成验证、Trace 和 Evaluation 做运行治理。当前默认使用 SQLite，也实现了可选 PostgreSQL shared durable store；Supervisor 和执行 ownership 仍在进程内，项目还不是分布式 Runtime 或公共百万 QPS SaaS。

## 2. 90 秒项目介绍

我主要解决三个问题。第一，Agent 长任务如何不因进程退出、Tool 副作用或多 Agent 并发而失控：我用 Run/Checkpoint CAS、ToolExecution 和 durable Child Run 保存状态，用预算和无进展检测约束循环。第二，模型怎样安全获得外部能力：ToolRegistry/Executor 统一本地与 MCP Tool，并在写操作前做 HITL、路径/命令校验和审计。第三，怎样证明效果：代码检索有固定 Recall@5/MRR 数据集，Runtime 有 Trace/Span 和多 trial Evaluation，Badcase 经人审后进入 Regression。

我会主动说明边界：PostgreSQL 解决跨进程共享真相，不解决谁有权执行；Active Run ownership 仍在单进程内；Guard 不是沙箱；外部写 Tool 不能保证通用 exactly-once；模型输出 final 也不等于完成已验证。

## 3. 五条简历原句

1. 设计复杂任务编排机制，支持 ReAct、Plan-and-Execute 及多 Agent 协作模式；按任务依赖图（DAG）拆分任务并基于 asyncio 调度就绪节点，单批最多并发执行 4 个只读工具、写操作串行控制，在固定工具 I/O 基准下较串行执行耗时降低约 74%。

2. 设计统一工具执行层，集中管理文件、Shell、Web 抓取、代码检索及 MCP 等不同类型工具，并支持 stdio / Streamable HTTP 两种接入方式；通过敏感操作人工审批、路径与命令校验，并以 JSONL 记录操作审计日志，约束工具执行范围并保留完整操作记录。

3. 构建 Code Intelligence，基于 tree-sitter AST 分块与 SHA-256 增量索引，融合 FTS5 / BM25 与 Embedding 检索并通过 RRF 排序，结合符号解析与调用关系补充跨文件上下文；建立 lexical / vector / hybrid 固定离线检索集，以 Recall@5 / MRR 做检索回归。

4. 通过 Durable Store contract 在默认 SQLite 或可选 PostgreSQL 中持久化 Run / Checkpoint / ToolExecution / Event / control state，在模型调用与工具执行边界保存状态；两后端都用原子 CAS 拒绝 stale write，并以稳定 invocation、显式 retry state、UTC backoff deadline 和安全抑制支持断点恢复。

5. 构建 Runtime API 与运行评测链路，支持任务暂停、恢复、取消及 SSE 事件重放，并通过 Trace / Span 记录模型与工具调用链路；针对同一任务进行重复试验，基于任务完成条件与失败样例，持续评估任务成功率与工具调用正确性，及时发现版本退化。

## 4. 18 个最高频问题

### 1. Tool 成功但 Checkpoint 前挂了怎么办？

若 `SUCCEEDED` 已落库就复用；若远端成功但本地仍 `RUNNING`，结果是 UNKNOWN，普通写不能盲重试。

### 2. invocation ID 是否保证 exactly-once？

不保证。它提供逻辑身份和已完成结果复用；外部效果仍需下游 idempotency key、status query 或补偿。

### 3. resume 和 cancel 冲突怎么办？

先成功提交合法 durable transition 的一方生效；另一方冲突或读取终态。CAS 防 stale overwrite，Task 跟随 durable state。

### 4. CAS 解决什么、不解决什么？

它比较 checkpoint sequence，防旧写覆盖新写；不等于锁、Worker ownership，也不能阻止 CAS 前双执行 Tool。

### 5. Checkpoint 为什么选语义边界？

每 token 写放大且是半语义状态；固定 timer 可能截在无意义中间态。LLM/Tool/control 边界可重建且频率有界，但仍有 crash window。

### 6. Checkpoint 和 Event 有什么区别？

Event 记录“发生过什么”，服务历史/审计/SSE replay；Checkpoint 记录“从哪里继续”。两者不能互相替代。

### 7. 为什么先 SQLite、现在加 PostgreSQL？为什么不是 Redis？

SQLite 适合本地 Runtime：部署简单、事务完整、小写并发下迭代快。PostgreSQL 让多进程共享 Run/Checkpoint/ToolExecution/Event 真相，并提供跨进程条件更新和短事务。Redis 可辅助协调或通知，但这些记录是 durable correctness truth，不应只依赖临时协调缓存。

当前口径：PostgreSQL backend 与 contract tests 已实现，但当前任务环境没有测试 DSN，20 个真库用例仍跳过；因此不能说 real PostgreSQL integration 已验证。

### 8. PostgreSQL 后两个 Worker 就不会执行同一 Run 吗？

不会。当前只有共享状态、Checkpoint CAS 和 ToolExecution 唯一记录；没有 claim、lease、heartbeat、fencing。CAS 拒绝 stale state write，但不能撤回 CAS 前已经发生的两个外部调用；ToolExecution 唯一约束也不等于外部 exactly-once。

### 9. PostgreSQL CAS、Event ID 和故障怎么处理？

CAS 用单条 `UPDATE runs SET current_sequence=N+1 ... WHERE run_id=? AND current_sequence=N RETURNING`，受影响为零就是 stale writer；head 更新和 Checkpoint history insert 同事务。Event ID 用 BIGINT identity，按 ID replay，要求单调排序而不要求 gapless。配置 PostgreSQL 却连接失败时显式失败，绝不静默切 SQLite，以免产生两份 durable truth。

### 10. 服务重启后谁接管 Run？

当前由显式 resume 重建；Supervisor 是进程内 registry。自动接管需要共享库、lease、heartbeat、recovery scan 和 fencing。

### 11. 父 Run cancel 后 Child 怎么办？

Plan/Multi-Agent 会取消非终态 Child、保留已完成 Child；传播不是原子事务。父落库后 crash 时，显式 Child resume/执行 preflight 会检查 durable ancestors 并收敛取消；自动后台 Recovery Scanner 仍未实现。

### 12. timeout 为什么不等于失败？

远端可能已完成只是响应丢失；`FAILED != UNKNOWN`。只有只读/下游幂等操作适合自动 retry。

### 13. logical invocation 和 physical attempt 有什么区别？

一个模型 Tool Call 是稳定 invocation；每次真实执行是 attempt。一次 invocation 可有 3 个 attempts，retry 仍占预算。

### 14. Agent 最终答案正确为什么还不够？

还要看 Tool 路径、参数、步骤、attempt、Token、成本、延迟、timeout 和恢复；final accuracy 不等于 Runtime quality。

### 15. Tool Selection / Argument Accuracy 怎么评？

Selection 用 acceptable/required/forbidden Tool set，不强制唯一 golden path；参数用 normalized/schema/subset/task predicate。当前只实现 required/forbidden usage，Argument Accuracy 是未来设计。

### 16. Repeated Trials 为什么必要？

采样、Tool 时序和 retry 有随机性；`trial_success_rate` 是独立重复成功比例，不是 Pass@k。

### 17. 成功率提高但成本翻倍怎么办？

同时看 quality、cost、latency、steps 与 reliability；功能 hard regression 阻断，性能按阈值 gate 或 warning。

### 18. PathGuard 为什么不是 sandbox？

它只做应用层路径授权；宿主 shell、网络、资源、凭证和子进程仍需容器/namespace、mount、egress、quota 和 secret broker。

## 5. 10 个必须主动声明的边界

1. 当前是本地/企业内部 Runtime，不是公共高 QPS SaaS。
2. ActiveRunSupervisor 与两个 Local Scheduler 都是进程内能力。
3. Checkpoint CAS 防旧写，不提供分布式 ownership。
4. SQLite 适合本地、零运维和小写并发；PostgreSQL 提供多进程共享状态和跨进程 CAS，但 lease/fencing 仍未实现。
5. ToolExecution 能复用已成功结果，不保证所有外部写 exactly-once；SQLite/PostgreSQL 都持久化 attempt、失败分类、显式 retry state、suppression reason、UTC `next_retry_at` 和累计 backoff，unsafe `UNKNOWN` restart 后仍禁止自动执行。
6. PathGuard、CommandGuard、HITL 不是操作系统沙箱。
7. 简化 MCP server 不代表完整覆盖协议；rich content 当前会文本化。
8. 静态调用图是启发式近似，不是编译器级真相。
9. 确定性离线 embedding 不代表生产语义质量。
10. 当前 SSE 是有限 stored replay 响应，不是持续 live subscription；模型 final 和基础设施错误率也不能单独证明任务质量。

7. Retrieval holdout：20 queries，用于留出验证。

## 9. 最后 5 分钟

只背五句话：

1. 我做的是长时间 Agent 执行治理，不是把一个聊天接口包装成微服务。
2. 并发必须受依赖、读写副作用和容量上限约束。
3. durable 的关键是保存边界、CAS 和 Tool 副作用语义，不是“用了 SQLite”。
4. 质量必须同时看任务成功、步骤、Token、延迟与每次成功成本。
5. 任何数字都带数据集、环境、范围和未覆盖项一起说。

## 10. 最危险的 12 个陷阱

1. `CAS != Worker ownership`：它防 stale write，不阻止外部双执行。
2. `invocation ID != exactly-once`：外部写仍需服务端幂等或状态查询。
3. `FAILED != UNKNOWN`：timeout 后副作用可能已经发生。
4. `Checkpoint != Event Log`：一个负责恢复，一个负责历史/重放。
5. `Checkpoint != filesystem snapshot`：它不会回滚 shell 改过的文件。
6. `asyncio Task != durable Run`：Task 随进程死亡，Run 状态仍在。
7. `logical invocation != physical attempt`：retry 不免费，attempt 仍记账。
8. `final answer accuracy != Agent quality`：还要看工具、效率和可靠性。
9. `one golden Tool path != always correct`：多条轨迹可能都满足任务。
10. `Guard != sandbox`：应用校验不是 OS 隔离。
11. `timeout != deadline`：前者限单 attempt，后者限 Run lifetime。
12. `40 recovered executions != 40 scenarios`：当前是 21 类 × 2，另有 2 次 expected-safe。
