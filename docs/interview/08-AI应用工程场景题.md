# Axiom AI 应用工程场景题

> 这不是一份术语清单，而是一份可以直接说出口的中文面试答案。第 1～5 册按简历经历讲当前 Runtime，第 6 册提供源码地图，第 7 册用于临场速查；本册集中回答“上线后怎样不崩、流量增长先坏哪里、怎样查 P99、怎样从本地 Runtime 演进成共享服务”。

文中使用三类边界标记：

- **【当前已实现】**：源码和测试已经覆盖；
- **【当前部分支持】**：只有本地或单进程能力，不能外推成分布式能力；
- **【未来设计】**：面试中的生产化方案，当前仓库没有实现。

## 一、先把 Axiom 的项目定位说准确

### 1. 一分钟项目介绍

如果面试官让我介绍项目，我会这样回答：

> Axiom 是一个面向本地或企业内部工具场景的 Agent Runtime。它的重点不是做一个公网百万 QPS 服务，而是把长时间 Agent 执行做得可恢复、可控制、可观察。
>
> 一次任务会被建模成持久化的 Run，规划任务或多 Agent Worker 会成为 Child Run。Runtime 通过 Checkpoint 和版本比较避免旧执行者覆盖新状态，通过 ToolExecution 记录处理工具调用的崩溃窗口，通过 Context Manager、Run Budget 和 Progress Detector 控制上下文、成本和死循环，再通过 Trace、Evaluation、Badcase 和 Regression Gate 形成质量闭环。
>
> 当前执行 ownership 仍在单 Runtime 进程内；durable truth 默认用 SQLite，也可配置 PostgreSQL shared store。Active Run Supervisor 只管理本进程的 asyncio Task。若面向 500 到 1000 名企业开发者，下一阶段是在现有执行内核外增加持久队列、Worker lease/heartbeat/fencing、准入、租户隔离和全局模型配额，而不是把“已有共享数据库”误说成分布式 Runtime。

```text
开发者
   ↓
Runtime API / CLI
   ↓
Durable Agent Runtime
   ↓
LLM / 内部工具 / MCP / 代码库
```

当前项目的优势集中在：执行持久化、上下文控制、成本控制、循环治理、工具安全、调用链证据、评测回归和代码检索。当前没有分布式 Worker 调度、全局租户配额或 Kubernetes 自动扩缩容，不是因为这些概念不重要，而是因为它们还不是当前工作负载的主要矛盾。

## 二、线上排障的通用六步法

我会记住一句话：

> **先看范围，接着拆链路，再看资源，再查依赖，先做止血，最后复盘。**

调用链追踪（Tracing）是把一次请求经过的 Runtime、LLM、工具、检索和数据库步骤串起来，并记录每一步耗时与结果。它解决的是“整次请求很慢，但不知道时间花在哪”的问题。例如总耗时 5 秒，如果调用链显示 4.2 秒都在等待某个 MCP 工具，就没有必要先优化数据库。

尾延迟（Tail Latency）指最慢那部分请求的延迟，P99 就是 99% 请求都不超过的时间。平均延迟正常而 P99 很高，常见原因是排队、少量慢依赖、锁竞争、重试或超大请求。因此排障不能只看平均值。

### 第一步：看影响范围

先问这是单个请求、单个租户、某一种 Tool、某个模型，还是所有请求都慢；是刚发布后发生，还是随着流量逐渐出现；P50、P95、P99 是一起升高，还是只有 P99 升高。范围判断能快速区分“公共依赖故障”和“少量异常输入”。

### 第二步：看整体指标

我会同时看请求量、错误率、P50/P95/P99、活动 Run 数、等待队列长度、CPU、内存、磁盘、连接池等待时间、LLM 429 比例和工具超时比例。这里的目标不是马上得出根因，而是判断系统是否处于流量突增、资源饱和或依赖异常。

### 第三步：拆调用链

从慢请求样本进入调用链，分别看入口等待、Runtime 自身处理、代码检索、上下文构造、LLM 首字时间、工具执行和 Checkpoint 写入。还要看这些步骤是串行还是并行，不能把并行步骤的耗时简单相加。最终要找到真正位于关键路径上的慢步骤。

### 第四步：用日志和资源确认原因

调用链告诉我“慢在哪里”，日志和资源指标回答“为什么慢”。例如数据库 Span 很慢，还要继续看是连接池排队、长事务、SQLite 写锁、磁盘 IO，还是 SQL 本身；LLM 很慢则看模型版本、输入 Token、429、重试和供应商状态。

### 第五步：先止血

根因没有完全查清之前，先保护系统。可以降低并发、暂停问题工具、限制新任务进入、熔断持续失败的依赖、把非关键功能降级、取消已经过期的卡死任务，或回滚刚发布的模型/配置。止血目标是缩小影响面，不是把错误隐藏成成功。

熔断（Circuit Breaker）的意思是：一个依赖连续失败时，系统暂时停止继续请求它，直接快速失败或走降级路径，给依赖恢复时间。例如 LLM 服务连续返回错误，如果还让每个请求等待 60 秒并重试三次，只会让队列更长；熔断后可以快速返回“模型暂不可用”，或路由到已经验证过的小模型。

### 第六步：长期修复与复盘

修复可能是调整超时、修连接池、补幂等、优化索引、增加容量、改准入规则，也可能只是补一个缺失的指标。最后要把真实失败转成可重复的测试。Axiom 可以把终态失败收集成 Badcase，经人工确认后提升为回归用例，这样复盘不会停留在一份事故报告里。

## 三、场景题库：线上故障排查（10 题）

### A1. Agent API 的 P99 从 800 毫秒突然升到 5 秒，怎么查？

**题目**

线上 Agent API 的 P99 突然从 800 毫秒升到 5 秒，你会如何调查？

**先给结论**

我不会第一时间猜数据库，也不会马上扩容。我会先确认是整体请求都变慢，还是少量尾部请求变慢，再按照“整体指标 → 调用链 → 日志和资源 → 依赖”的顺序定位；找到主要耗时后，才决定限流、回滚、降级、扩容还是修代码。

**完整回答**

第一步看故障范围和时间点。我会对比 QPS、错误率、P50/P95/P99、不同接口、模型、工具、租户和发布版本。如果 P50 仍然是 800 毫秒，只有 P99 到 5 秒，更像是少量请求排队、超大上下文、慢工具、锁竞争或重试；如果所有分位数一起上升，则更像公共依赖或整体资源饱和。

第二步抽取慢请求的调用链，拆出入口排队、Context 构造、检索、LLM 首字与生成、Tool、Checkpoint/数据库。假如 5 秒中有 4 秒在 LLM，就继续看输入 Token、模型版本、429 和重试；如果有 3 秒在队列，说明 Worker 或下游配额已经饱和；如果 SQLite 写入突然变慢，则看并发 Child Run、写事务和磁盘。

第三步才用日志和资源确认原因：CPU 是否打满，内存是否接近上限，事件循环是否阻塞，连接池是否有大量等待者，磁盘 IO 是否升高，LLM 或 MCP 是否正在故障。临时止血可以是回滚最近发布、降低并发、暂停慢工具、限制大请求或对故障依赖做熔断。长期修复要补上缺失的分层指标，并用相同负载重新测 P50/P95/P99。

**排查 / 设计步骤**

1. 对齐异常开始时间与发布、模型、配置和流量变化。
2. 按接口、租户、模型、工具和请求大小分桶比较延迟。
3. 从 P99 慢样本拆出排队时间与真正执行时间。
4. 检查 CPU、内存、磁盘、连接池、LLM、Tool 和数据库。
5. 先限流、降级或回滚，再做单变量验证和负载复测。

**如何结合 Axiom 回答**

【当前已实现】Axiom 的 RunTracer 会记录 Agent、LLM、Tool、Checkpoint、权限和进展相关 Span，LLM Span 里有首字时间、总延迟和 Token，RunMetrics 能看到步骤数、调用数、失败数和成本。这些证据可以帮助判断一条 Run 慢在哪一步。

**当前没有实现什么**

【当前部分支持】这些是本地持久化观测，还不是跨网关、队列、多个 Worker、MCP 服务和数据库的完整分布式调用链，也没有生产告警大盘和 SLO。

**如果继续扩展会怎么做**

【未来设计】我会统一传播 trace_id，在网关、准入队列、Worker、LLM 网关和 MCP 中记录耗时，补充队列长度、连接池等待、依赖限流和版本维度，再建立按 P99 和任务成功率触发的告警。

**面试官可能继续追问**

- **为什么先看 P50/P95/P99？** 因为它能判断是整体退化还是少数尾部异常，排查方向不同。
- **为什么不能直接扩容？** 如果瓶颈是 LLM 配额、MCP 或数据库锁，扩入口实例只会更快压垮下游。
- **临时怎么止血？** 回滚、降低并发、限制大请求、暂停问题依赖，并保证拒绝是明确可观察的。

### A2. Tool 调用频繁超时，怎样判断是哪一层的问题？

**题目**

Tool 调用突然大量超时，怎样区分是 Runtime、网络、MCP Server、内部 API、数据库还是连接池？

**先给结论**

我会先确定超时发生在“等待执行、建立连接、服务端处理、数据库访问还是返回结果”哪个阶段。不能看到 TimeoutError 就一律归因于网络，因为连接池排队、事件循环阻塞、MCP 内部慢查询都会在客户端表现成超时。

**完整回答**

先按 Tool 名称、MCP Server、租户和时间窗口统计超时。如果只有一个工具异常，优先查该工具及其下游；如果所有 Tool 都慢，要看 Runtime 的事件循环、Worker 并发和公共网络。然后从 Tool Span 往下拆：调用是否很久没有开始，DNS/TCP/TLS 是否慢，连接池获取是否等待，MCP `call_tool` 是否已经进入服务端，内部 API 和 DB 分别花了多久。

缩小范围时可以做受控对照：从同一网络环境直接调用 MCP 健康接口；用固定小参数调用问题 Tool；临时换掉内部 API 或数据库；比较冷连接与复用连接。这样能区分 Runtime 调度慢、网络慢和服务端业务慢。

临时止血可以降低该 Tool 的并发、缩短等待队列、暂停非关键 Tool、对持续失败的依赖熔断，或在策略允许时返回明确降级结果。长期要建立分层超时、连接复用、每个 Tool 的并发隔离和端到端调用链。超时后还必须取消下游工作，避免客户端已经放弃，服务端仍占资源。

**排查 / 设计步骤**

1. 按工具和依赖分组统计超时率与 P99。
2. 检查等待队列、事件循环和并发信号量。
3. 拆连接建立、连接池等待、MCP 处理、内部 API 和 DB 时间。
4. 用直连、小请求、替代依赖做隔离实验。
5. 降低并发或熔断止血，之后补分层超时和连接复用。

**如何结合 Axiom 回答**

【当前已实现】`McpClientManager` 有读取超时，Durable Runtime 还会用 Run 剩余 lifetime 截短每次 Tool timeout，只对只读/显式幂等 Tool 的暂态错误做有界重试。ToolExecution 持久化 attempt、失败类别、pending backoff 和 exhausted/suppressed 状态；Tool Span 能区分失败、等待、重试、成功与复用结果。

**当前没有实现什么**

【当前部分支持】Axiom 没有 MCP Server 内部、内部 API 和 DB 的跨服务追踪，也没有统一连接池指标或通用熔断器。

**如果继续扩展会怎么做**

【未来设计】进一步向每个远端协议传播 absolute deadline 和 trace_id，复用 HTTP/MCP 连接，并按真实服务规模决定是否增加每依赖连接池、并发隔离与 circuit breaker。当前不实现跨 Run 熔断状态。

**面试官可能继续追问**

- **所有超时都重试吗？** 不。只重试短暂且幂等的失败，写操作要先判断外部副作用是否可能已经发生。
- **连接成功为什么还会超时？** 服务端排队、慢 SQL、锁竞争或返回体过大都会造成读取超时。
- **怎样判断连接池耗尽？** 看活动连接、空闲连接、等待者数量、获取连接耗时和事务持有时间。

### A3. LLM 大量返回 429，怎么处理？

**题目**

LLM Provider 突然大量返回 429，你会怎样止血和长期治理？

**先给结论**

429 表示供应商正在限制请求、Token 或并发，不应该让所有请求立刻重试。我会先降低进入模型的并发，把可等待任务放进有上限的队列；重试必须有次数上限、指数退避和随机抖动，并优先遵守服务端返回的 Retry-After。

**完整回答**

先确认配额维度：是每分钟请求数、每分钟 Token、同时连接数，还是账户额度。Agent 的一个用户请求可能触发多次 LLM 调用，所以 HTTP QPS 不高也可能耗尽模型配额。我会按模型、租户和 Run 统计真实调用数、输入/输出 Token、429 比例和排队时间。

指数退避是每次失败后逐步延长等待，例如 1 秒、2 秒、4 秒、8 秒，避免持续轰击故障依赖。随机抖动是在这个等待时间上加入随机量，因为如果一万请求都恰好在第 4 秒重试，会形成新的流量尖峰。即使有退避，也必须设置总截止时间、最大次数和全局重试预算。

临时止血是降低模型并发、暂停低优先级批任务、缩短不必要的上下文，必要时路由到经过评测的备用模型。持续 429 时应该熔断，而不是让请求在队列里无限等待。长期要在 LLM 网关做全局与租户配额，并用实际 Token 完成预留和结算。

**排查 / 设计步骤**

1. 区分 RPM、TPM、并发和账户额度限制。
2. 统计每 Run 的模型调用次数与 Token 分布。
3. 立即降低准入和模型并发，限制队列长度。
4. 对安全请求采用 Retry-After、指数退避、随机抖动和次数上限。
5. 建立全局/租户配额、熔断和质量可验证的备用模型。

**如何结合 Axiom 回答**

【当前已实现】RunBudget 能限制一棵 Run tree 的模型调用、Token、wall time 和成本；Runtime 自己发起的重试会再次计入预算和 Trace，不会被当成免费操作。失败按 timeout、connection、429、selected 5xx、validation、auth、policy 等类别确定性分类，退避采用有上限的指数 full jitter；下一次等待超出剩余 deadline 时不再重试。

**当前没有实现什么**

【当前部分支持】当前 `RetryPolicy` 是 per-operation 本地策略，不是全局模型限流、共享 circuit breaker、服务级 backpressure 或租户配额系统；SDK/HTTP 内部隐藏重试只有在依赖显式暴露时才能被 Runtime 统计。

**如果继续扩展会怎么做**

【未来设计】在 LLM 网关加入全局并发信号量、按模型的请求/Token 限流、租户公平队列、配额反馈和备用供应商路由。

**面试官可能继续追问**

- **为什么重试会让故障更严重？** 原请求没有消失，又多出重试流量，容易形成重试风暴。
- **为什么指数退避还要抖动？** 退避只把流量推迟；没有随机量，客户端仍会在同一时刻再次冲击。
- **一直失败怎么办？** 达到截止时间或熔断阈值后快速失败或降级，不能无限重试。

### A4. Agent 进程内存连续上涨，怎么查？

**题目**

Agent 进程运行几个小时后内存一直增加，你会如何判断是正常高水位还是泄漏？

**先给结论**

我会先把内存曲线和活动 Run 数、asyncio Task 数、消息历史、Tool 输出、Trace 缓冲和缓存大小对齐。还要区分“对象真的没有释放”和“Python 分配器已经释放对象但没有把 RSS 还给操作系统”，不能只看进程内存就断言泄漏。

**完整回答**

先做固定并发的长时间压测。如果活动 Run 数上升时内存同步上升，任务结束后能回落或稳定，可能是正常工作集；如果 Run 已完成、Supervisor handle 和 Task 数仍不断增长，就要找生命周期清理问题。对象快照可以比较哪些类型持续增加，例如 Message、Tool result、Span、HTTP response 或 Task。

Agent 特别容易积累原始消息、超大 Tool 输出、检索文档和 Trace。Axiom 的 Context compaction 只缩小“发给模型的投影”，不会删除 Checkpoint 和完整 ToolExecution，因此不能把 prompt 变小等同于进程内存或数据库变小。还要检查流式响应、MCP session、HTTP client、文件句柄和子进程是否正确关闭。

临时止血可以降低活动 Run 上限、拒绝超大 Tool 结果、重启达到内存阈值的 Worker，并保护已经持久化的 Run。长期要加入每 Run 内存/结果大小限制、artifact 外置、Trace 保留策略、任务清理测试和内存压力下的准入控制。

**排查 / 设计步骤**

1. 对齐 RSS、堆大小、活动 Run、Task、缓存和句柄数量。
2. 比较任务开始、结束和空闲一段时间后的对象快照。
3. 检查 raw messages、Tool 输出、Context、Trace 和检索缓存。
4. 检查 done callback、流式连接、MCP session、子进程与文件是否关闭。
5. 降低并发止血，并用长时间稳定负载验证修复。

**如何结合 Axiom 回答**

【当前已实现】ActiveRunSupervisor 能列出本进程活动 Run，并在完成时注销；ContextManager 会投影历史大 Tool 输出、限制模型输入；Checkpoint 仍保存可恢复事实。

**当前没有实现什么**

【当前部分支持】没有生产级堆分析、每租户内存配额、artifact 存储或 Trace 生命周期管理。

**如果继续扩展会怎么做**

【未来设计】加入 worker 级内存水位、每 Run 资源画像、结果外置、定期回收和基于内存压力的准入；Worker 重启前先停止接收并安全排空任务。

**面试官可能继续追问**

- **Context 压缩为什么不能解决所有内存问题？** 它只改变模型输入投影，不会删除持久状态或其他对象引用。
- **RSS 不下降一定是泄漏吗？** 不一定，可能是分配器保留内存，需要结合对象数量判断。
- **怎么临时止血？** 限制并发和单任务大小，安全轮换 Worker，而不是直接杀掉有副作用的任务。

### A5. SQLite 写入突然变慢，怎么查？

**题目**

Checkpoint 或其他 SQLite 写入延迟突然升高，你会如何分析？

**先给结论**

SQLite 同一时刻主要还是单写者模型，所以我会优先检查写竞争、事务时间、Checkpoint 频率和磁盘，而不是先改 SQL。Axiom 的并发 Child Run、ToolExecution、预算账本和 Trace 都可能增加写入；优化时不能为了延迟随意删掉关键恢复边界。

**完整回答**

先按表和操作类型统计写入次数、P99、事务耗时、锁等待、数据库大小、WAL 文件和磁盘 IO。如果最近平均 Child 并发或每 Run 步骤数增加，即使请求数没变，Checkpoint 写 QPS 也可能显著增加。长事务或一次序列化超大状态，也会让其他写者等待。

Axiom 的 `SQLiteCheckpointStore` 使用 WAL、30 秒 busy timeout 和 `BEGIN IMMEDIATE`，Checkpoint 以 `(run_id, sequence)` 追加并检查版本。这很适合本地可靠性，但不意味着可以让很多进程高并发共享写。临时可以降低 Child 并发、限制大结果、暂停非关键评测写入并确认磁盘健康。不能直接把 durable write 改成异步丢弃。

长期先缩短事务、审计索引和状态大小，把非关键观测与关键执行状态区分存储。当前也可切到 PostgreSQL shared backend；切换后仍要用真实数据库重验 sequence CAS、ToolExecution、Event 与预算账本语义，并根据负载调小型 bounded pool。

**排查 / 设计步骤**

1. 分别统计 Checkpoint、ToolExecution、预算和 Trace 的写入量。
2. 查看事务时长、锁等待、WAL、磁盘空间和 IO 延迟。
3. 对齐步骤数、Child 并发和单条状态大小。
4. 先降低写并发或非关键负载止血。
5. 保留恢复语义，优化短事务或规划共享数据库迁移。

**如何结合 Axiom 回答**

【当前已实现】SQLite 的 WAL/busy timeout 与 PostgreSQL bounded pool/条件 UPDATE 都有明确实现；两后端共享 Checkpoint、ToolExecution、预算、Event 和 control contract。

**当前没有实现什么**

【当前部分支持】已有多实例可见的 PostgreSQL durable backend 和连接池，但当前任务环境尚未通过真库 integration gate；没有分片、独立 Trace 管道、ownership 或生产 SLA。

**如果继续扩展会怎么做**

【未来设计】先在 CI/测试服务中通过 PostgreSQL integration gate，再按访问模式验证索引与池等待；下一阶段另做 queue/lease/fencing，并把大量观测数据拆到独立存储或批量管道。

**面试官可能继续追问**

- **为什么 WAL 还会写竞争？** WAL 改善读写并发，但不能让多个写事务真正同时提交。
- **能否降低 Checkpoint 频率？** 可以审计冗余写，但不能破坏 Tool、终态和策略转换的持久边界。
- **换 PostgreSQL 就都解决了吗？** 不会，热点行、长事务和连接过多仍会造成竞争。

### A6. Worker 在 Tool 执行中崩溃，怎样恢复？

**题目**

Runtime Worker 在调用 Tool 的过程中崩溃，当前系统能保证什么，不能保证什么？

**先给结论**

我会把“本地确认成功”和“外部可能成功但本地未知”分开。Axiom 可以复用已经持久化为成功的 ToolExecution；但如果外部写操作已经发生，Worker 在保存成功结果前崩溃，Runtime 不能凭 Checkpoint 证明外部状态，因此不能声称通用 exactly-once。

**完整回答**

恢复时先加载最新 Checkpoint，再按 `run_id + tool_call_id` 形成稳定操作唯一 ID，读取 ToolExecution 并核对参数哈希。如果记录已经是 SUCCEEDED，就直接复用结果并继续，不重新执行。这个机制覆盖了“工具成功记录已保存，但后续 Checkpoint 还没写”的窗口。

最危险的是记录仍为 RUNNING。以创建工单为例，服务端可能已经创建成功，只是在回包时 Worker 崩溃。对于只读 Tool，重试一般安全；对于明确接受幂等键的 Tool，可以把稳定 invocation_id 传给下游；否则必须查询下游状态，或进入人工批准，不能盲重试。

多 Worker 场景还要先确认旧 Worker 已失去执行权。即使新 Worker 从 Checkpoint 恢复，如果旧 Worker 因网络恢复又继续写，也可能双执行，所以未来需要租约和递增令牌阻止旧 Worker。

**排查 / 设计步骤**

1. 加载最新 Checkpoint 和对应 ToolExecution。
2. 核对操作唯一 ID、工具名和参数哈希。
3. SUCCEEDED 直接复用；RUNNING 按只读、幂等或未知分类。
4. 未知写副作用通过状态查询或人工确认处理。
5. 用故障注入测试每个崩溃窗口。

**如何结合 Axiom 回答**

【当前已实现】`ToolExecutionRecord`、稳定 invocation_id、参数哈希、成功结果复用，以及未知副作用进入 approval 的恢复路径都已实现。Runtime 还会记录 Tool Span 和 retry count。

**当前没有实现什么**

【当前部分支持】没有下游系统通用的 exactly-once 保证，也没有多 Worker 自动接管和 fencing token。

**如果继续扩展会怎么做**

【未来设计】共享 ToolExecution 存储；对写 Tool 强制幂等键或状态查询协议；Worker 使用租约和递增令牌；对无法自动判定的操作保留人工恢复。

**面试官可能继续追问**

- **Checkpoint 和幂等键有什么区别？** Checkpoint 记录本地执行位置；幂等键让外部系统识别重复操作。
- **为什么 CAS 不能保证 exactly-once？** CAS 只防本地旧状态覆盖，不能回滚或证明外部副作用。
- **旧 Worker 恢复怎么办？** 未来用递增 fencing token，让共享存储拒绝旧所有者的写入。

### A7. 模型升级后 Agent 平均步骤数翻倍，怎么查？

**题目**

模型升级后平均 Agent step 数突然翻倍，你怎样判断这是能力提升还是循环退化？

**先给结论**

步骤数增加不一定是坏事，关键要同时看任务成功率、工具路径、Token、成本和无进展信号。我会先确认候选版本究竟改变了模型、提示词、工具描述还是 Context 策略，再用相同数据集做多次独立试验和单变量对比。

**完整回答**

先按 case、模型和执行策略比较步骤分布，而不是只看总平均。若少数复杂任务步骤增加但成功率明显提高，可能是更深入推理；若重复相同 Tool、相同错误或 A-B-A-B 短循环增加，则是退化。还要排查工具变慢或返回错误，模型可能因此增加自我修复步骤。

我会查看 Trace 中每步的 LLM 决策、Tool 调用和 ProgressDetector 计数，把失败 trial 收成 Badcase。版本指纹能说明模型、提示词、工具 schema、权限、Context 或预算配置是否不同，但指纹变化只是定位线索，不是因果证明。最终通过只改变一个变量的实验确认。

临时可以回滚模型或限制最大步骤，长期应把代表性失败提升为回归用例，同时监控 trial success rate、平均步骤、Token 和 Cost per Success，避免只优化一个资源指标。

**排查 / 设计步骤**

1. 核对模型、提示词、工具和策略版本。
2. 按 case 比较步骤、成功率、Token、成本和工具轨迹。
3. 查看重复动作、重复错误、短循环和稳定状态。
4. 做独立多次试验与单变量回滚。
5. 审核 Badcase，并加入回归门禁。

**如何结合 Axiom 回答**

【当前已实现】RunMetrics、ProgressDetector、Evaluation repeated trials、Badcase、版本归因和 Regression Gate 已经能形成这条证据链。

**当前没有实现什么**

【当前部分支持】当前没有线上自动金丝雀、统计显著性检验，也不能用一个哈希变化自动证明根因。

**如果继续扩展会怎么做**

【未来设计】增加模型版本看板、线上小流量对照、任务类型分桶和统计置信区间，再按成功率和单位成功成本共同决策。

**面试官可能继续追问**

- **为什么不能只设 max_steps？** 它只能限制最多做多少，不能判断每一步是否有进展。
- **步骤少一定好吗？** 不一定，过早结束可能让成功率下降。
- **怎样证明模型导致变化？** 固定其他配置做单变量、重复试验。

### A8. 请求量没变，但 Token 成本翻倍，怎么查？

**题目**

请求量没有变化，但 Token 成本突然翻倍，你会检查哪些因素？

**先给结论**

请求数不等于模型工作量。我会把成本拆成模型调用次数、每次输入 Token、每次输出 Token、缓存 Token 和模型单价，先找是哪一项变化，再结合步骤数、检索上下文和 Tool 输出判断原因。

**完整回答**

输入成本上涨常见于系统提示词或 Tool schema 变长、检索 top-k 增加、历史消息累积、超大 Tool 输出进入上下文或压缩没有及时触发。输出成本上涨可能是输出上限或模型行为变化。调用次数上涨通常与平均步骤、重试或子 Agent 数增加有关；即使 Token 不变，换了更贵模型或价格表变化也会让美元成本上涨。

我会按模型、版本、case 和租户比较实际输入/输出 Token、模型调用次数、Context 压缩前后估算、缓存命中、retrieval size、重试数和单价。临时可以限制大上下文、减少非必要输出、停止异常重试或回滚配置。长期要把成本和任务成功率放在一起看，因为少 Token 但成功率更低，单位成功成本反而可能更高。

**排查 / 设计步骤**

1. 拆调用次数、输入、输出、缓存 Token 和单价。
2. 对比步骤数、重试数、Child 数量和模型版本。
3. 检查检索内容、消息历史、Tool 输出和压缩次数。
4. 核对价格配置与缓存计价。
5. 止住异常增长，并用 Cost per Success 验证优化。

**如何结合 Axiom 回答**

【当前已实现】BudgetManager 会用 Provider 返回的实际 usage 结算输入、输出、缓存和推理 Token；价格使用本地显式配置，未知价格保持 unknown。Context Span 会记录压缩前后估算。

**当前没有实现什么**

【当前部分支持】没有企业级租户成本大盘、全局支出上限或自动拉取实时模型价格。

**如果继续扩展会怎么做**

【未来设计】增加按模型、租户、任务类型的成本看板、预算告警、全局 spend cap 和缓存命中指标。

**面试官可能继续追问**

- **为什么未知价格不能按零？** 零会制造“免费”的错误结论，应该明确标成未知。
- **怎样判断压缩是否值得？** 同时比较任务成功率、约束保留和单位成功成本。
- **重试算不算成本？** 真实发出的模型请求都应计入。

### A9. Multi-Agent Child Run 卡住，怎么定位？

**题目**

多个 Child Run 中有一些一直不结束，你会检查什么？

**先给结论**

我会先从持久状态判断它是在合法等待，还是已经失去执行者，而不是只看状态字段写着 RUNNING。重点检查 Child 状态和最后更新时间、Supervisor 是否还有活动 Task、Tool/LLM 是否在等待、预算和无进展状态，以及 Parent 是否卡在汇合或审查阶段。

**完整回答**

先按 parent_run_id 列出所有 Child。WAITING_APPROVAL 可能是在等人，WAITING_CHILD 可能是在等依赖，RUNNING 则要确认当前进程是否真有 owner handle。如果数据库显示 RUNNING 但进程重启后 Supervisor 中没有 Task，这只是崩溃前遗留状态，不能证明它仍在工作。

接着查对应 LLM、Tool 和 Checkpoint Span，以及 ToolExecution 是否长期 RUNNING；再看 Child 本地预算、根 Run 聚合预算、wall time 和 ProgressDetector。最后检查 Parent 的任务依赖、join、review 或 synthesis 是否已经满足却没有完成 reconciliation。

临时可以取消明确卡死且无危险副作用的任务、人工处理未知写 Tool、降低 Child 并发并恢复 Parent。长期在共享服务中需要心跳、租约过期、卡死检测和原子接管。

**排查 / 设计步骤**

1. 列出 Parent/Child lineage、状态、序列和最后更新时间。
2. 对比 Supervisor 活动 handle 与持久化 RUNNING 状态。
3. 查 LLM、Tool、approval、预算和无进展检测。
4. 检查 Parent 的 join、review、synthesis 和状态汇合。
5. 安全取消或恢复，并为失去 owner 的 Run 设计接管。

**如何结合 Axiom 回答**

【当前已实现】Child 有稳定 ID、独立 Checkpoint/Trace/Progress，并共享根预算；Parent 有持久化 reconciliation 逻辑，Supervisor 可查看本进程活动任务。

**当前没有实现什么**

【当前部分支持】没有跨进程心跳、租约、孤儿 Run 扫描器或自动接管。

**如果继续扩展会怎么做**

【未来设计】持久化 Worker 所有权与租约；租约过期后新 Worker 通过版本比较接管；加入队列年龄、最后心跳和卡死原因指标。

**面试官可能继续追问**

- **RUNNING 为什么不一定真在运行？** 进程可能在下一次写状态前崩溃。
- **一个 Child 卡住要取消所有兄弟吗？** 不一定，应由 Parent 的依赖和失败策略决定。
- **怎么避免重复接管？** 用共享数据库的原子 claim 和递增版本号。

### A10. 任务成功率下降，但基础设施错误率正常，怎么解释？

**题目**

部署后 HTTP 错误率没有变化，但 Agent 任务成功率下降，你会怎么查？

**先给结论**

HTTP 200 只说明服务返回了结果，不说明结果正确。Agent 可能选错工具、漏掉约束、检索到错误证据、陷入低质量自我修复，或者过早声称完成，所以必须把基础设施可用性和任务质量分开观察。

**完整回答**

我会先用稳定的任务数据集做基线与候选版本对比，查看 required scorer、trial success rate、Tool usage、步骤、Token、延迟和成本。然后进入失败 Run 的 Trace，确认是检索、工具选择、权限、Context 压缩、模型行为还是完成判定发生变化。

版本指纹可以帮助确认模型、公开配置、提示词、Tool schema、权限、Context 或预算是否改变。对失败案例要人工判断：它可能是真缺陷，也可能是 Provider 故障、环境问题或测试预期错误。确认后再把 Badcase 提升为回归用例。

临时可以回滚模型或提示词，暂停有问题的路由。长期应建立任务型 SLO、金丝雀评测和用户反馈闭环，而不是只盯 HTTP 错误率。

**排查 / 设计步骤**

1. 对相同任务做基线/候选独立多次试验。
2. 比较成功率、required scorer、工具轨迹和资源指标。
3. 核对版本与配置指纹。
4. 检查失败 Run 的检索、Context、Tool 和完成证据。
5. 人工审核 Badcase，回滚止血并补回归。

**如何结合 Axiom 回答**

【当前已实现】Evaluation 走真实 Durable Runtime，保留每个 trial 的 Run/Trace；Badcase 经过人工审核后才能进入 Regression Gate。

**当前没有实现什么**

【当前部分支持】已有基于显式确定性 Completion Contract 的 Runtime verifier；没有通用语义 verifier、线上业务指标平台或自动语义评判系统。

**如果继续扩展会怎么做**

【未来设计】只在具体任务需要时扩展确定性契约；生产化再考虑线上抽样评测、用户反馈和版本金丝雀，并把基础设施 SLO 与任务成功 SLO 分开。

**面试官可能继续追问**

- **为什么不用 LLM 自动判断所有答案？** Judge 本身也会漂移，需要确定性检查和人工证据兜底。
- **错误率正常还要回滚吗？** 如果核心任务成功率显著下降，业务上仍然应该回滚。
- **Run COMPLETED 等于任务成功吗？** 不等于，它只表示 Runtime 正常终止。

## 四、性能优化：先找到时间花在哪里

性能优化最容易犯的错误，是还没测量就开始加缓存、加并发或换数据库。我的方法是：先测量，再拆延迟，找到占比最大的部分，判断它属于 CPU、内存、磁盘、网络、数据库、队列、检索、LLM、Tool、序列化还是锁竞争，然后只优化关键路径。优化后必须用相同请求分布和并发重新测 P50/P95/P99、吞吐、错误率、资源占用和任务成功率。

### 1. 延迟拆解

可以把一次 Agent 请求近似写成：

```text
总延迟 =
入口处理和排队
+ 检索
+ 上下文构造
+ 模型首字时间
+ 工具调用
+ 模型生成
+ 持久化与其他开销
```

这个式子是思考框架，不代表所有步骤都串行。BM25 和向量召回可以并行，多个独立只读 Tool 也可以并行，因此真正决定总时间的是关键路径。例如 LLM 首字需要 900 毫秒，优化一个 20 毫秒 SQL 到 5 毫秒，对 2 秒总延迟几乎没有意义。

### 2. 并行执行

并行适合相互独立、主要在等待网络或磁盘的任务。例如同一个查询同时做 BM25 和向量召回，或者同时读取三个互不依赖的代码文件，串行可能是 100+120+80 毫秒，并行后关键路径更接近最慢的 120 毫秒。

不能并行的情况也很明确：B 的输入依赖 A；多个写操作有顺序要求；Tool 不是并发安全的；或者下游已经满载。并行也不一定提高吞吐，因为它只是把更多工作同时压给下游。若数据库最多稳定处理 50 个查询，同时发 500 个只会增加排队和锁竞争。Axiom 当前只并行标记为只读且并发安全的 Tool，并通过信号量限制数量；Plan DAG 也只执行依赖已经满足的节点。

### 3. 缓存

缓存的本质是用存储换重复计算。RAG 中可以有查询结果缓存、Embedding 缓存、检索结果缓存、文档内容缓存和模型稳定提示词前缀缓存。例如同一份代码文件内容没有变化，就没有必要反复生成相同 Embedding。

难点不是“放进 Redis”，而是缓存键和失效规则。检索缓存至少要包含租户、权限、索引版本、查询和参数；文档变更或权限变化后必须失效，否则会返回旧答案甚至跨租户泄漏。写 Tool 通常不能用普通结果缓存。Axiom 的 ToolExecution 复用是为了同一次 invocation 的崩溃去重，不是跨请求通用缓存，面试时要分清。

### 4. 批处理

批处理是把多个同类小请求合成一次执行。比如 32 段文本分别请求 32 次 Embedding，会重复承担网络往返和设备调度；如果 Provider 支持批量接口，一次发送 32 段通常吞吐更高、单位成本更低。

代价是等待凑批。第一个请求可能要等后面 31 个，所以批处理常常提高吞吐，却让单请求延迟变差。在线系统通常设置“最大批大小”和“最长等待时间”，到任一条件就发出；严格低延迟请求可以绕过批处理。离线评测、索引构建和低优先级观测数据比交互请求更适合批处理。

### 5. 连接复用和连接池

每次请求都重新建立 TCP/TLS、认证和数据库连接会产生额外延迟，也会制造端口和服务端资源压力。连接复用让多个请求共享已建立的连接；连接池则用一个有上限的连接集合控制并发。

连接池不是越大越好。池太小，请求会长时间等连接；池太大，数据库会同时处理过多事务，CPU、锁竞争和上下文切换变严重，P99 反而上升。正确做法是观察连接获取等待、活动/空闲连接、事务时长和数据库饱和点，用压测找到合适区间。

### 6. 异步执行

异步主要解决等待型任务的并发问题，不会让 CPU 计算本身变快。一个协程等待 LLM 或 MCP 网络响应时，事件循环可以去推进其他 Run，因此少量线程也能管理较多 I/O 请求。但如果某段 Python 代码长时间占用 CPU 又不让出执行权，它仍会阻塞事件循环，需要进程池、线程池或独立服务。

Axiom 的 Durable Runtime 和 ToolExecutor 使用 asyncio，SQLite 同步操作通过线程执行。这让等待型工作可以交错，但仍必须限制并发；无界创建协程只会把压力转移到内存、连接池和下游。

### 7. 索引优化

数据库索引解决的是“怎样少扫描数据”。要根据过滤、连接和排序字段设计，并用执行计划确认是否使用；索引太多会增加写放大。Elasticsearch 的重点是分词、倒排索引、分片数、过滤条件和候选规模，不能只盯一个 top-k。向量检索通常使用近似最近邻索引，需要在召回率、构建成本、内存和查询延迟之间调参。

Axiom 的代码检索还要区分候选召回和最终上下文：BM25 找精确符号，向量找语义相似，symbol/call graph 补结构邻居。优化时既测本地延迟，也要测 Recall@K、MRR 和最终任务成功率。

### 8. 模型侧优化

模型路径可以通过减少无价值输入、限制不必要输出、选择更快模型、缓存稳定提示词前缀、按任务难度路由模型和流式返回来优化。减少输入与输出、换快模型可能真正降低总时间；流式返回通常只是让用户更早看到第一个字，改善感知延迟，不代表完整答案更早结束。

任何模型优化都要和质量一起测。一个小模型虽然快 50%，但如果成功率明显下降，用户重试和人工修复会让整体成本更高。Axiom 的 Context、RunMetrics 和 Evaluation 可以提供这类对照证据。

## 五、场景题库：性能优化（10 题）

### B1. RAG/Agent P99 是 2 秒，怎样降到 300 毫秒？

**题目**

一个 RAG/Agent 请求 P99 是 2 秒，你如何把它优化到 300 毫秒？

**先给结论**

我不会上来就承诺一定能从 2 秒降到 300 毫秒，第一步一定是先把这 2 秒拆开。还要先问 300 毫秒指完整答案、模型首字，还是只指检索接口；如果一次外部 LLM 首字本身就要 900 毫秒，那么 300 毫秒完整返回在当前约束下并不现实。

**完整回答**

我会先用调用链得到一个假设性分解，注意这些数字只是演示，不是 Axiom 的生产实测：

```text
入口：       20 ms
检索：      250 ms
重排：      200 ms
模型首字：  900 ms
工具：      400 ms
其他：      230 ms
```

这时最重要的结论不是“每层都优化一点”，而是模型首字和工具占据关键路径。即使把数据库优化 20 毫秒，也无法接近 300 毫秒。若业务要求 300 毫秒看到反馈，可以先在几十毫秒内返回已受理或检索摘要，再流式输出模型结果；但必须说明这改善的是感知延迟，不是完整请求总延迟。

如果拆解后发现检索占主要时间，我会让 BM25 与向量召回并行，缩小候选集，调近似向量索引，并缓存稳定的 Embedding 和检索结果；重排只处理少量高质量候选。如果 Tool 占主要时间，就进一步拆连接池等待、连接建立、服务端执行和响应大小，做连接复用、只读结果缓存、并发限制和更合理的超时。如果排队占主要时间，就不是优化函数，而是限制任务准入、增加真正受约束资源的 Worker，或减少单 Run 占用时间。

LLM 侧可以减少无价值上下文、投影大 Tool 结果、限制输出、使用更快模型、使用提示词缓存或按任务复杂度路由。但换模型后必须做多次评测。最终我会给出分阶段目标，例如先把检索 P99 从 450 毫秒降到 180 毫秒，把首字从 900 降到 500，再将用户可感知首响应压到 300 毫秒；如果完整结果仍需 1 秒，就诚实说明物理边界。

**排查 / 设计步骤**

1. 澄清 300 毫秒是首字、检索还是完整结果。
2. 拆入口、排队、检索、重排、Context、LLM、Tool 和持久化。
3. 找到 P99 关键路径，而不是按平均占比猜测。
4. 分别验证并行检索、候选缩减、连接复用、Context 缩减和模型路由。
5. 在目标并发下重测 P50/P95/P99、错误率、任务成功率和成本。

**如何结合 Axiom 回答**

【当前已实现】Axiom 有 hybrid retrieval、有限的代码上下文、LLM/Tool/Checkpoint Span、首字时间、Context 压缩，以及只读且并发安全 Tool 的有界并行，可以帮助建立真实延迟分解。

**当前没有实现什么**

【当前部分支持】没有生产级缓存层、ANN 服务、长期连接池、模型路由器、任务准入队列或经过负载验证的 300 毫秒 SLO。

**如果继续扩展会怎么做**

【未来设计】补完整调用链和关键路径分析；增加版本化检索/Embedding 缓存、持久连接、LLM 路由、热 Worker 与有界队列；按真实任务分布做负载和质量回归。

**面试官可能继续追问**

- **为什么不直接换小模型？** 小模型可能降低成功率，必须通过相同任务的多次评测验证。
- **流式返回算优化吗？** 它优化首字和感知延迟，但不一定减少完整生成时间。
- **并行检索为什么不一定更快？** 下游 CPU、网络或索引已经饱和时，并行会增加竞争。
- **怎样证明达到 300 毫秒？** 在目标并发和真实数据分布下报告 P99，而不是单机空载的一次结果。

### B2. 怎样建立完整的 Agent 延迟分解？

**题目**

你会如何测量一次长 Agent 请求到底慢在哪？

**先给结论**

我会把“等待时间”和“真正执行时间”分开，再把每个 Agent step 拆成检索、Context、LLM、Tool 和持久化。长 Agent 总延迟可能是每一步都不慢，但步骤数翻倍，因此既要看单步 P99，也要看每 Run 的步骤分布。

**完整回答**

入口先记录准入和队列等待；Run 内用同一 trace_id 串联 Agent、LLM、Tool 和 Checkpoint；LLM 还要区分首字时间与完整生成时间。并行步骤要画出父子关系，不能直接求和。最后按模型、工具、策略、租户、版本和请求大小分桶，避免快请求掩盖慢类型。

**排查 / 设计步骤**

1. 定义统一 Span 类型和时间边界。
2. 记录队列等待、活动执行和人工等待。
3. 区分 LLM 首字、生成、Tool 与数据库。
4. 标出并行关系和真正关键路径。
5. 按请求类型统计各分位数。

**如何结合 Axiom 回答**

【当前已实现】本地 Trace 覆盖 Run、step、LLM、Tool、Checkpoint、权限和进展检测，RunMetrics 会聚合次数、Token 和延迟。

**当前没有实现什么**

【当前部分支持】没有入口队列、多服务传播和统一生产看板。

**如果继续扩展会怎么做**

【未来设计】统一跨服务 trace_id，把队列、连接池和依赖状态作为 Span 属性，并从 P99 样本链接到日志和指标。

**面试官可能继续追问**

- **为什么 Span 不能简单相加？** 并行步骤时间会重叠，简单相加会重复计算。
- **为什么要记录请求大小？** 大 Context、大 Tool 输出通常拥有不同延迟分布。

### B3. 哪些工作适合并行，哪些不适合？

**题目**

怎样判断 Retrieval 或 Tool 能否并行执行？

**先给结论**

只有互不依赖、不会破坏副作用顺序、下游还有容量的工作才适合并行。并行减少的是串行等待，不会凭空增加数据库、LLM 或 MCP 的处理能力，因此必须有并发上限。

**完整回答**

BM25 和向量召回读同一个查询但互不依赖，可以并行；读取几个独立文件也可以。写文件后再运行测试存在先后关系，不能并行；两个修改同一资源的 Tool 可能产生竞态，也不能只看“都是异步函数”就并行。判断时我会画依赖 DAG，标出只读、并发安全和共享资源，再用信号量保护下游。

**排查 / 设计步骤**

1. 画出输入输出依赖。
2. 标记只读、写入和并发安全属性。
3. 确认下游容量和限额。
4. 设有界并发、超时和取消传播。
5. 测总延迟、吞吐和尾延迟。

**如何结合 Axiom 回答**

【当前已实现】ToolExecutor 只并行 `is_read_only && is_concurrency_safe` 的调用；Plan DAG 只调度依赖已满足的任务。

**当前没有实现什么**

【当前部分支持】这是本地并发，不是跨 Worker DAG 调度或全局 Tool 配额。

**如果继续扩展会怎么做**

【未来设计】调度器根据依赖、Tool 配额和 Worker 容量发放任务，按依赖隔离并发。

**面试官可能继续追问**

- **无界 gather 有什么问题？** 会造成内存、连接和下游瞬时过载。
- **并行一定提高吞吐吗？** 不一定，下游饱和时只会增加竞争。

### B4. Agent/RAG 中哪些内容适合缓存？

**题目**

怎样设计查询、Embedding、检索、文档和提示词缓存？

**先给结论**

我只缓存可稳定寻址、重复率高、计算昂贵且允许一定陈旧的内容。最重要的不是 Redis 选型，而是缓存键包含哪些版本和权限，以及文档、索引或权限变化后如何失效。

**完整回答**

Embedding 缓存可以用内容哈希加模型版本做 key；检索缓存需要查询、租户、权限、索引版本和检索参数；文档缓存需要文档版本；提示词缓存适合稳定 system prompt 和 Tool schema 前缀。强实时数据、跨租户敏感结果和写操作不适合普通缓存。还要防止热点 key 同时失效造成缓存击穿，并监控命中率、陈旧错误和内存占用。

**排查 / 设计步骤**

1. 评估重复率、计算成本和陈旧风险。
2. 设计包含租户、权限、版本和参数的 key。
3. 定义失效、TTL 和容量上限。
4. 防击穿并记录命中/未命中。
5. 用任务质量验证缓存结果。

**如何结合 Axiom 回答**

【当前已实现】ToolExecution 会复用同一次稳定调用的已确认结果；Code Index 和参数哈希提供版本化思路。

**当前没有实现什么**

【当前部分支持】没有跨请求的生产缓存，也不能把 ToolExecution 去重宣传成通用缓存。

**如果继续扩展会怎么做**

【未来设计】优先做 Embedding 与只读检索缓存，按 tenant 和 index version 隔离；再根据命中率决定是否增加 Tool 缓存。

**面试官可能继续追问**

- **缓存最危险的问题是什么？** 权限或版本没进入 key，导致旧数据甚至跨租户泄漏。
- **为什么写 Tool 不缓存？** 它的结果常代表外部状态变化，不能把旧结果当新执行。

### B5. Context 太大导致 LLM 首字变慢，怎么优化？

**题目**

模型输入上下文越来越长，首字延迟和成本都上升，你会怎么做？

**先给结论**

先验证输入 Token 与首字延迟的相关性，再删除“无价值重复”，而不是粗暴截断。目标、约束、最近消息、未完成 Tool 协议和计划状态要保留，历史大结果可以投影或外置。

**完整回答**

我会检查 system prompt、Tool schema、检索 top-k、历史消息、Tool 输出和压缩次数。优化顺序通常是去重检索、收紧 Context 预算、把历史大 Tool 结果变成带来源的摘要、复用稳定前缀缓存，再考虑更快模型。压缩前后要做相同任务的多次评测，确认约束、证据和任务成功率没有明显下降。

**排查 / 设计步骤**

1. 对比估算和实际输入 Token。
2. 找出重复提示词、检索和大 Tool 输出。
3. 保留不可压缩状态，压缩旧前缀。
4. 测提示词缓存和更快模型。
5. 同时回归质量、首字、总延迟和成本。

**如何结合 Axiom 回答**

【当前已实现】ContextManager 在每次模型调用前估算、压缩、重新估算，保护 Tool 消息原子性并投影历史大结果；超出 hard limit 时不调用 Provider。

**当前没有实现什么**

【当前已实现】固定 10-case Context Retention 数据集分别检查 objective、constraints、open tasks、decisions、artifact references、critical evidence 和协议状态，报告 required-state retention、protocol integrity、压缩前后 Token 与 compression ratio，并支持确定性 compressed-vs-uncompressed outcome probe。

**如果继续扩展会怎么做**

【当前边界】确定性 retention harness 能证明声明的 required items 是否保留，不能证明开放域语义完全等价；当前没有 LLM Judge。artifact-backed Tool result 和查询感知检索路由仍是独立未来方向。

**面试官可能继续追问**

- **为什么不直接保留最近 N 条？** 一条 Tool 结果可能比几十条短消息更大，固定条数不反映 Token 风险。
- **怎样证明没有“压缩变笨”？** 分开看结构/协议不变量、required-state retention、compression ratio，以及可确定时压缩/未压缩任务结果；仍不能声称通用语义等价。

### B6. Tool 很慢，应该用异步、连接池还是缓存？

**题目**

一个 Tool 延迟很高，你如何选择优化手段？

**先给结论**

先拆成排队、连接、服务端计算、数据库和响应传输。异步提高等待期间的并发利用，连接复用减少建连成本，缓存避免重复执行；三者都不能修复慢 SQL 或已经饱和的下游。

**完整回答**

如果时间主要花在 TCP/TLS 或 session 初始化，优先复用连接；如果是大量 I/O 等待且下游有余量，使用异步和有界并发；如果同一只读结果重复率高且允许陈旧，才做缓存。如果服务端计算或 DB 锁占主导，应修服务端或降低并发。选择后要同时观察 Tool P99 和下游饱和度。

**排查 / 设计步骤**

1. 拆连接池等待、建连、服务端和返回时间。
2. 判断 I/O、CPU、DB 或下游容量瓶颈。
3. 选择连接复用、异步、缓存或服务端优化。
4. 设置超时与并发上限。
5. 在并发负载下复测。

**如何结合 Axiom 回答**

【当前已实现】Runtime 是异步的，MCP 有超时，ToolExecutor 有并发边界。

**当前没有实现什么**

【当前部分支持】不是统一的持久 HTTP/MCP 连接池或 Tool 缓存平台。

**如果继续扩展会怎么做**

【未来设计】按依赖建立长生命周期客户端、独立连接池指标和只读缓存，再根据压测调整。

**面试官可能继续追问**

- **异步会让单次调用更快吗？** 通常不会，它主要让等待时间可以服务其他任务。
- **为什么不能无限加连接？** 会超过服务端容量，增加锁竞争和超时。

### B7. Checkpoint 写入成为 P99 关键路径，能少写吗？

**题目**

持久化写入很慢，是否可以降低 Checkpoint 频率？

**先给结论**

可以消除重复写、优化事务和分离非关键观测，但不能随意删除恢复边界。每减少一次同步写，都要回答“在这个窗口崩溃后会重复什么、丢失什么”，并重新做故障注入测试。

**完整回答**

我会分别测 Checkpoint、ToolExecution、预算账本和 Trace，判断哪个真的在关键路径。Tool 开始/成功、策略状态转换和终态通常需要同步持久化；某些高频观测可以批量或异步，但不能反过来让已发生副作用失去记录。还可以缩短事务、减少状态冗余和优化索引。

**排查 / 设计步骤**

1. 按写类型测频率、大小和 P99。
2. 标记必须同步的持久边界。
3. 优化序列化、事务和索引。
4. 仅批量非关键观测。
5. 重跑崩溃恢复测试。

**如何结合 Axiom 回答**

【当前已实现】Checkpoint append-only、ToolExecution 与预算 CAS 都有明确顺序和 crash-window tests。

**当前没有实现什么**

【当前部分支持】没有按 durability class 分层的独立写入管道。

**如果继续扩展会怎么做**

【未来设计】关键执行状态进入共享事务库，Trace 进入独立可批量管道，同时保留端到端关联 ID。

**面试官可能继续追问**

- **为什么 Trace 可以异步而 ToolExecution 不行？** 前者主要用于观测，后者决定是否安全重放副作用。
- **怎样验证少写安全？** 在每个新窗口注入崩溃，检查恢复和重复执行。

### B8. 怎样同时优化代码检索质量和延迟？

**题目**

Code Intelligence 检索慢或召回差，应该怎么调？

**先给结论**

先区分“候选里根本没有正确文档”和“候选有，但排序或上下文构造丢了”。延迟优化不能只缩 top-k，还要同时守住 Recall@K、MRR 和最终 Agent 成功率。

**完整回答**

精确 symbol、错误字符串适合 BM25；自然语言意图适合向量；调用关系适合 symbol/call graph。可以并行稀疏和向量召回，融合后只重排小候选，再做有界图扩展。参数在 development set 上调，最终用 holdout 验证，防止对题库过拟合。索引新鲜度和版本化缓存同样重要。

**排查 / 设计步骤**

1. 按查询类型分析 Badcase。
2. 分别测 candidate recall 与最终排序。
3. 并行不同召回并缩小重排集。
4. 检查索引新鲜度和缓存。
5. 在 holdout 与真实任务上验证。

**如何结合 Axiom 回答**

【当前已实现】AST chunk、BM25/向量、symbol、call graph 和有界 CodeContextBuilder，以及离线检索基准。

**当前没有实现什么**

【当前部分支持】离线 hash embedding 只证明流程，不代表生产语义模型质量；没有在线检索服务 SLO。

**如果继续扩展会怎么做**

【未来设计】查询类型路由、真实 embedding/index 服务、增量索引与线上任务反馈。

**面试官可能继续追问**

- **为什么不全用向量？** 精确符号和错误字符串通常更适合倒排检索。
- **召回高就够了吗？** 不够，噪声上下文会增加 Token 并误导模型。

### B9. 批处理怎样权衡延迟和吞吐？

**题目**

Embedding 或观测写入要不要做批处理？

**先给结论**

批处理适合追求吞吐的同质工作，但会增加等待凑批时间。在线低延迟请求要设置最大批大小和最长等待，过期或高优先级请求可以绕过；不能只看每秒处理量。

**完整回答**

例如 32 个 Embedding 请求合成一批，减少 31 次网络和设备调度开销，GPU 利用率可能更高。但低流量时第一个请求可能为了凑批白等几十毫秒；不同长度混批还会有填充浪费和队头阻塞。评估时同时报告吞吐、队列等待和 P99。

**排查 / 设计步骤**

1. 确认任务同质且 Provider 支持批量。
2. 设置最大批大小和最长等待。
3. 按模型、长度和优先级分组。
4. 支持到期绕过和单项错误定位。
5. 同时测吞吐与尾延迟。

**如何结合 Axiom 回答**

【当前已实现】Evaluation 当前顺序执行，以减少 Provider 限流和 SQLite 竞争，这体现了吞吐优化需要服从依赖边界。

**当前没有实现什么**

【当前部分支持】没有在线动态批处理器。

**如果继续扩展会怎么做**

【未来设计】优先在离线索引或 Embedding 服务做微批处理，而不是先改变交互式 Run。

**面试官可能继续追问**

- **批越大越好吗？** 不，等待、填充和队头阻塞会恶化 P99。
- **哪里最适合先试？** 离线 Embedding 和非关键观测写入。

### B10. 怎样证明优化不是一次偶然结果？

**题目**

做完性能优化后，你怎样验证收益可信？

**先给结论**

固定数据、版本、并发和运行环境，保留基线，预热后重复测试，并同时报告延迟分位数、吞吐、错误、资源饱和和任务成功率。一次本机空载结果不能证明生产收益。

**完整回答**

我会分成微基准、组件负载、端到端和长时间稳定性测试。明确冷缓存和热缓存，逐步提高并发找到吞吐拐点；外部 LLM 有噪声时保留每次 trial，而不是只报最好的一次。若速度提高但 success rate 降低，应视为质量回归而不是成功优化。

**排查 / 设计步骤**

1. 固定 workload 和版本并记录基线。
2. 区分冷启动、预热和稳定阶段。
3. 多并发点重复运行。
4. 同时报 P50/P95/P99、错误、资源和质量。
5. 加故障注入和长时间压测。

**如何结合 Axiom 回答**

【当前已实现】Evaluation comparison 分离质量、Token、步骤、延迟和成本，检索与恢复也有固定基准。

**当前没有实现什么**

【当前部分支持】没有生产负载平台、自动金丝雀或完整统计显著性分析。

**如果继续扩展会怎么做**

【未来设计】建立可重复负载环境、持续性能回归、版本分桶和 SLO burn-rate 告警。

**面试官可能继续追问**

- **为什么平均值不够？** 它会掩盖少量极慢请求和过载拐点。
- **怎样控制 Provider 噪声？** 重复试验、记录版本，并把网络噪声和本地计算分别测量。

## 六、流量与稳定性治理：把系统保护在容量以内

这一组概念可以用两条链记住：

```text
流量突然增加
  → 限流
  → 任务准入与有界队列
  → 背压
  → Worker 执行

依赖持续异常
  → 超时
  → 有条件重试 + 指数退避 + 随机抖动
  → 熔断
  → 降级或明确失败
```

超时解决“最多等多久”，重试解决“短暂失败是否值得再试”，熔断解决“依赖持续失败时不要继续浪费资源”，隔离解决“一个坏依赖不能拖垮全部任务”，限流控制允许进入的数量，背压（Backpressure）解决“下游处理不过来时，上游必须减速”，过载保护则是在容量不足时优先保住核心请求。

## 七、场景题库：流量与稳定性治理（8 题）

### C1. 怎样设计超时层级？

**题目**

Agent API、LLM、Tool、数据库分别应该怎样设置超时？

**先给结论**

每个外部依赖都必须有截止时间，否则一个永远不返回的调用会一直占住协程、连接和 Run。外层请求要把“剩余时间”向内传播，内部操作的超时必须小于剩余总时间；超时后还要真正取消下游工作。

**完整回答**

我会区分连接超时、读取超时、单次操作超时、整次 Run 的活动时间和人工等待。比如客户端允许 70 秒，网关 65 秒，当前 Run 执行片段 60 秒；进入某个 Tool 时只剩 15 秒，就不能仍给它固定 60 秒。等待批准可以把 Run 持久化后释放执行资源，不应该一直保持 HTTP 连接。

超时值来自延迟分布和业务价值，而不是所有层统一 30 秒。太短会误杀正常慢请求，太长会放大故障和队列。日志和 Span 要明确记录在哪一层超时，是否发出了取消，以及下游是否响应取消。

**排查 / 设计步骤**

1. 画出客户端、网关、队列、Run、LLM、Tool 和 DB 的时间预算。
2. 传递绝对截止时间，而非每层重新计时。
3. 区分连接、读取、操作和生命周期超时。
4. 超时后传播取消并记录阶段。
5. 根据真实 P99 和误杀率调整。

**如何结合 Axiom 回答**

【当前已实现】LLM、MCP/Tool 有局部超时配置，RunBudget 可以限制 wall time，interrupt/Checkpoint 能把等待态持久化。

**当前没有实现什么**

【当前部分支持】没有跨网关、队列和多服务的统一 deadline propagation。

**如果继续扩展会怎么做**

【未来设计】在请求上下文保存绝对截止时间，队列任务过期自动失效，Worker 将剩余时间传给 LLM/MCP/DB，并确保取消传到底层。

**面试官可能继续追问**

- **为什么外层超时不能和内层一样？** 外层先结束后，内层仍继续运行会浪费资源。
- **长 Agent 怎么办？** 返回异步 Run handle，通过查询/事件获取进度，而不是保持无限长 HTTP 请求。
- **超时后都能重试吗？** 不能，写操作可能已经在外部成功。

### C2. 重试怎样设计，为什么会出现重试风暴？

**题目**

哪些错误可以重试，怎样避免重试把系统压垮？

**先给结论**

只有短暂、幂等、仍在总截止时间内的失败才适合自动重试。每次重试都要计入次数、Token 和成本，并使用指数退避、随机抖动、最大尝试次数和全局重试预算；持续失败时必须熔断。

**完整回答**

网络连接重置、临时 503、部分 429 可能重试；参数错误、权限拒绝、确定性业务失败没有必要重试。对于写操作，超时不能证明失败，必须依赖幂等键、状态查询或人工确认。

重试风暴的形成很直观：原来每秒 1000 个请求，下游开始失败，每个请求再试两次，下游可能看到接近 3000 次尝试。若所有客户端固定等 4 秒，它们会在同一时刻再次到达。指数退避让间隔按 1、2、4、8 秒增长，随机抖动再把同一批请求打散；重试预算则限制系统中“由重试产生的流量比例”。

**排查 / 设计步骤**

1. 建立可重试和不可重试错误分类。
2. 检查操作是否幂等且剩余时间足够。
3. 设置最大次数、退避、抖动和 Retry-After。
4. 限制每依赖的重试并发和总预算。
5. 持续失败时熔断，恢复时少量探测。

**如何结合 Axiom 回答**

【当前已实现】Runtime 重试会计入预算；Tool 只有只读或声明 `idempotency_key_parameter` 时才会自动重试，成功记录恢复时不会重复扣一次 Tool call。

**当前没有实现什么**

【当前部分支持】当前没有跨进程重试预算、随机抖动和通用熔断中间件。

**如果继续扩展会怎么做**

【未来设计】把依赖错误分类、退避、抖动、重试预算和熔断统一到 LLM/MCP 客户端策略，并让每次尝试进入 Trace。

**面试官可能继续追问**

- **所有 GET 都能重试吗？** 通常更安全，但仍要看下游成本、时效和是否真的无副作用。
- **为什么不能多层重试？** SDK、Runtime、网关各重试三次会产生乘法放大。
- **熔断后怎样恢复？** 半开状态只放少量探测请求，成功后逐步恢复。

### C3. 熔断和降级怎样配合？

**题目**

LLM Provider 持续失败时，熔断器应该怎样工作？

**先给结论**

超时只限制一次请求，熔断是在一段时间内失败或慢调用过多时暂时停止新请求，避免每个 Run 都重复等待。熔断后可以快速失败，也可以走经过质量验证的备用模型；降级结果必须明确标记。

**完整回答**

例如最近 30 秒内 LLM 调用达到最小样本量后，失败率或慢调用比例超过阈值，熔断器进入 open 状态，新的低优先级请求不再访问该 Provider。等待一段时间后进入 half-open，只放少量探测；成功率稳定再逐渐关闭熔断。健康检查只能说明探针可用，真实请求的 Token 大小和延迟仍可能异常，所以判断应结合真实流量。

降级可能是切换到小模型、返回只含检索证据的结果或让用户稍后重试。不能为了 HTTP 200 隐瞒质量下降，应该记录 fallback_model、原因、任务成功和成本。

**排查 / 设计步骤**

1. 按 Provider/模型建立独立失败与慢调用统计。
2. 设置最小样本、阈值和打开时间。
3. 半开时限制探测数量。
4. 设计明确可接受的降级路径。
5. 用 Eval 验证降级质量并逐步恢复。

**如何结合 Axiom 回答**

【当前已实现】LLM Span、RunError 和 Evaluation 能提供失败、延迟和备用模型质量证据。

**当前没有实现什么**

【当前部分支持】没有通用熔断器或自动模型降级路由。

**如果继续扩展会怎么做**

【未来设计】在 LLM 网关按模型维护熔断状态，并将降级版本写入 Trace 与评测归因。

**面试官可能继续追问**

- **熔断和限流区别？** 限流保护容量；熔断针对依赖健康异常。
- **备用模型一定能用吗？** 不一定，必须验证任务质量、权限与成本。

### C4. 限流、任务准入和背压有什么区别？

**题目**

如果一秒进入 100 个长任务，但 Runtime 只能稳定处理 20 个，怎么办？

**先给结论**

我不会让 100 个任务全部立刻开始。入口先按用户和全局配额限流，再根据当前活动 Run、内存、模型和 Tool 容量决定哪些任务准入；其余进入有上限、有过期时间的队列，队列满后明确拒绝。

**完整回答**

限流控制某个时间窗口允许多少请求或 Token，例如每用户每分钟 30 个 Run、整个模型每分钟 10 万 Token。任务准入关注“此刻是否有能力开始”，即使用户没超过配额，Worker 已满也应该排队。

背压的核心是下游处理不过来时，上游不能无限塞任务。生产者每秒 100、消费者每秒 20，若不限制，队列每秒净增 80，最终内存、连接和等待时间都会失控。背压可以表现为调用方等待、队列只接收一定数量、返回 429/503 或建议稍后重试。大队列不是容量，它只是把立即失败变成长时间超时。

**排查 / 设计步骤**

1. 分别定义用户、租户、全局和依赖配额。
2. 用活动 Run、队列年龄、内存和依赖 slot 做准入。
3. 只保留有上限、有过期时间的队列。
4. 向调用方返回清晰的等待或拒绝信号。
5. 监控队列增长速度和清空时间。

**如何结合 Axiom 回答**

【当前已实现】RunBudget 管理单棵 Run tree 内的工作量，不是入口流量控制。

**当前没有实现什么**

【当前部分支持】没有共享限流、准入队列或跨 Worker 背压。

**如果继续扩展会怎么做**

【未来设计】增加租户令牌桶、有界持久队列、Worker 容量上报和排队过期；交互任务与批任务分优先级。

**面试官可能继续追问**

- **为什么不建无限大队列？** 到达速度长期大于处理速度时，任何有限资源最终都会耗尽。
- **队列满了怎么办？** 保护已接受任务，明确拒绝低优先级新任务并给重试建议。
- **RunBudget 能替代限流吗？** 不能，它限制一项任务，不限制同时进入多少任务。

### C5. 怎样用隔离避免一个 Tool 拖垮全系统？

**题目**

代码搜索 Tool 卡死时，怎样防止它占满整个 Agent Runtime？

**先给结论**

隔离（Bulkhead）就是把共享资源分成几个有边界的舱室。代码搜索 Tool 只能使用自己的并发信号量、连接池或 Worker 配额，即使它全部卡住，LLM 调用、文件读取和其他租户仍保留资源。

**完整回答**

我会按依赖和任务类型划分资源，例如交互任务与批任务分队列，代码搜索与写 Tool 分并发上限，大租户不能占光全局名额。隔离过细会造成资源闲置，所以可以保留一部分共享弹性，但每类必须有硬上限和超时。

**排查 / 设计步骤**

1. 找出共享线程、协程、连接、内存和下游配额。
2. 按 Tool、租户和优先级划分并发边界。
3. 设置独立超时、队列和连接池。
4. 保留有限共享余量。
5. 观察各分区利用率与拒绝率。

**如何结合 Axiom 回答**

【当前已实现】ToolExecutor 有本地并发信号量和读/写安全判断。

**当前没有实现什么**

【当前部分支持】这不是多租户资源隔离，也没有每个 MCP Server 独立 Worker 池。

**如果继续扩展会怎么做**

【未来设计】为不同 Tool/租户建立独立并发、连接池和队列，调度器保留核心任务容量。

**面试官可能继续追问**

- **隔离为什么不按租户完全独占？** 完全独占利用率低，应在硬上限外保留共享弹性。
- **只设超时够吗？** 不够，超时前仍可能占满所有资源。

### C6. 什么时候应该做过载保护？

**题目**

系统容量已经接近上限，应该丢弃哪些工作？

**先给结论**

过载保护（Load Shedding）是在系统即将失控前主动拒绝一部分低价值工作，保住核心请求和已经接受的任务。优先丢弃已过截止时间、低优先级、可重建或批处理任务，不能静默丢失一个已经持久化的 Run。

**完整回答**

触发信号可以是队列年龄、活动 Run、内存、连接池等待或 LLM 配额超过安全水位。临时拒绝新批任务，通常比随机杀死正在执行写 Tool 的 Run 安全；后者可能制造外部副作用未知窗口。拒绝结果要记录原因和是否可重试，避免客户端无脑重放。

**排查 / 设计步骤**

1. 定义核心、普通和可延迟任务。
2. 设置容量水位和拒绝条件。
3. 优先清理过期排队任务。
4. 保护已接受的高价值 Run。
5. 压测过载后的恢复速度。

**如何结合 Axiom 回答**

【当前已实现】durable cancel、interrupt 和结构化终态可以明确记录任务为何停止；RunBudget 能阻止单 Run 无界消耗。

**当前没有实现什么**

【当前部分支持】没有服务级优先队列和自动过载保护。

**如果继续扩展会怎么做**

【未来设计】按租户、优先级、截止时间和队列年龄做准入，拒绝事件进入审计和指标。

**面试官可能继续追问**

- **为什么不随机拒绝？** 会伤害核心任务，也不利于公平和可解释性。
- **已经执行的任务能直接杀吗？** 要考虑持久状态和 Tool 副作用，优先在安全边界取消。

### C7. 数据库连接池应该怎样设置？

**题目**

有 1000 个并发请求，是否需要 1000 个数据库连接？

**先给结论**

不需要，而且通常很危险。请求并发和数据库并发是两个不同概念，很多请求正在等 LLM 或 Tool，并不占数据库；连接池应该匹配数据库能够稳定处理的并发和事务持有时间。

**完整回答**

假设 1000 个请求中，平均只有 5% 的时间访问数据库，那么同时需要数据库的请求远少于 1000。可以先让每个 Worker 使用 20 个连接，观察连接获取等待、事务 P99、DB CPU、IO 和锁。如果池只有 5，连接等待可能很长；如果直接开到 500，数据库同时处理太多事务，锁竞争和上下文切换会让所有请求更慢。

长事务尤其危险，因为它不仅占连接，还可能长期持锁。优化顺序是缩短事务、减少不必要访问、让池等待进入调用链，然后在数据库吞吐拐点以内调池大小。多实例还要算全局连接数：20 个实例每个 50 个连接，就是 1000 个连接。

**排查 / 设计步骤**

1. 测量每请求访问 DB 的比例和连接持有时间。
2. 观察池的活动、空闲、等待和超时。
3. 观察 DB CPU、IO、锁和事务 P99。
4. 从较小池开始压测，找到吞吐拐点。
5. 计算所有实例的总连接预算。

**如何结合 Axiom 回答**

【当前已实现】SQLite 每次操作建立本地连接并使用短事务、WAL 和 busy timeout；PostgreSQL backend 使用默认 1～4 个连接的小型 bounded psycopg pool，不会让 1000 个 Run 等于 1000 个连接。

**当前没有实现什么**

【当前部分支持】已有 PostgreSQL 应用池，但没有连接代理、多实例全局连接预算、pool-wait Trace 或容量压测。

**如果继续扩展会怎么做**

【未来设计】用真库压测校准每 Worker pool 和全局连接预算，必要时加连接代理，并把 pool wait 加入 Trace。

**面试官可能继续追问**

- **池太小会怎样？** 请求在获取连接时排队，应用 P99 上升。
- **池太大会怎样？** 数据库过载、锁竞争增加，吞吐不升反降。
- **怎么确定数值？** 用事务时长、DB 容量和目标并发做压测，不靠固定经验值。

### C8. 依赖部分失效时怎样降级？

**题目**

向量检索、LLM 或可选 reviewer 故障时，Agent 应怎样继续服务？

**先给结论**

先区分依赖是任务必需还是可选。可选能力可以按预先定义的策略降级，必需写操作不能伪造成功；任何降级都要进入结果和调用链，并单独观察质量。

**完整回答**

向量检索失败可以只使用 BM25，但要标记召回能力下降；大模型不可用可以切换经评测的小模型；可选 reviewer 不可用时，只有策略明确允许才能跳过。如果任务必须调用内部写 API，则应该明确失败或等待恢复，不能生成一段看似成功的文本。

Redis 缓存故障时可以绕过缓存访问源服务，但要限并发，避免缓存故障把数据库打垮。恢复时也应逐步切回，防止瞬间流量冲击。

**排查 / 设计步骤**

1. 为依赖标记 required/optional。
2. 预先定义降级结果和质量边界。
3. 用独立超时、熔断和隔离触发。
4. 记录降级原因、版本和成功率。
5. 恢复时逐步放量。

**如何结合 Axiom 回答**

【当前已实现】结构化 Tool error、RunError、hybrid retrieval、Trace 和 Eval 可以保存降级证据并评估结果。

**当前没有实现什么**

【当前部分支持】没有共享服务级的自动降级路由器。

**如果继续扩展会怎么做**

【未来设计】建立按任务策略选择的 fallback，所有降级进入版本归因和质量门禁。

**面试官可能继续追问**

- **降级为什么还要测质量？** 技术上返回不等于任务正确，小模型或 BM25-only 可能降低成功率。
- **Redis 挂了为什么不能直接全打 DB？** 瞬时源站流量可能远超数据库容量，需要限流和请求合并。

## 八、为什么写操作不能无脑重试

考虑这个很典型的场景：

```text
Agent 调用了“创建工单”API。

服务端已经成功创建工单，
但返回结果时网络断开。

Agent 看到的是 timeout。
```

如果 Runtime 把超时简单理解成“没有执行”，马上再调用一次，工单就可能创建两次。这不是网络重试能自动解决的问题，而是“外部副作用已经发生，但本地不知道结果”的不确定窗口。

第一种解决方式是幂等键。Runtime 为这次逻辑操作生成稳定的操作唯一 ID，下游以它作为唯一约束。即使同一个请求发两次，下游也只创建一张工单并返回同一结果。第二种方式是状态查询：超时后拿操作 ID 去查询是否已经成功。第三种是在无法自动判断时暂停 Run，请人工确认，而不是赌一次重试。

Axiom 的 `ToolExecutionRecord` 会记录 invocation_id、参数哈希、状态和结果。若成功记录已经落库，恢复时直接复用；若记录还停在 RUNNING，Tool 又不是只读或没有幂等键，Runtime 会把它视为副作用未知并进入批准路径。这个设计能诚实处理本地恢复，但最终幂等仍需要外部系统配合。

面试追问可以这样答：

- **为什么数据库事务不能一起解决？** Runtime 的 SQLite 事务无法和外部工单系统组成同一个原子事务。
- **操作 ID 怎么生成？** 必须对同一次逻辑调用稳定，例如基于 run_id 和 tool_call_id，而不是每次重试生成新 ID。
- **幂等记录保留多久？** 至少覆盖调用方可能重试的最长时间，并结合业务审计要求。
- **如果下游不支持幂等也不能查询呢？** 只能保守暂停并人工确认，不能声称 exactly-once。

## 九、容量规划：把“流量大”换算成真实资源

容量规划最重要的公式是：

```text
并发量 ≈ QPS × 平均处理时间
```

它背后的直觉是：每秒进入 500 个请求，每个请求平均在系统里停留 2 秒，那么第一秒进来的 500 个还没走，第二秒又进来 500 个，稳定时大约有 1000 个请求同时存在。这个并发量包括等待和执行，不等于 1000 个线程，也不等于 1000 个数据库连接。

得到并发量后，才能继续问：一个实例在目标 P99 下能安全承受多少活动请求？需要多少实例和故障余量？每个请求会发几次 LLM，模型 RPM/TPM 和并发够不够？每个 Run 占多少内存和工作区？访问数据库的比例和事务时长是多少？有界队列在峰值时会积压多久？

Agent 系统还要单独计算生命周期并发。每秒只创建 10 个 Run，看起来 QPS 很低；若每个 Run 平均持续 60 秒，则约有 600 个 Run 同时存在。它们可能不都占 CPU，但会占 Checkpoint、消息、工作区、预算状态，还会在不同时间争用 LLM 和 Tool。

## 十、场景题库：容量规划（6 题）

### D1. 500 QPS、平均 2 秒，需要多少并发能力？

**题目**

接口峰值 500 QPS，平均延迟 2 秒，怎样估算容量？

**先给结论**

用 Little's Law 的直观形式计算，大约有 `500 × 2 = 1000` 个请求同时在系统中。但这只是第一步，不能直接推出 1000 个线程、连接或某个固定实例数；还要拆执行阶段和每种资源的占用比例。

**完整回答**

假设一个实例在真实负载下，保持目标 P99 时最多安全管理 50 个 I/O 型活动请求，那么理论上至少需要 20 个实例。生产还要考虑单实例故障、突发流量和发布余量，不能跑到 100% 饱和。这个“50”必须来自负载测试，不是经验拍脑袋。

接着分别核对 CPU、内存、LLM 配额、Tool 并发和数据库。如果请求的大部分时间在等 LLM，CPU 可能很空，但模型并发先耗尽；如果每个请求只在 5% 时间访问 DB，连接池不需要 1000；如果请求包含大 Context，内存可能先成为瓶颈。最后还要用峰值而非日均流量，并检查队列在峰值后多久能清空。

**排查 / 设计步骤**

1. 明确峰值 QPS、平均/P99 延迟和突发持续时间。
2. 估算总 in-flight，并拆等待与活动执行。
3. 压测单实例安全并发和吞吐拐点。
4. 分别校验模型、Tool、DB、CPU 和内存。
5. 加故障余量并计算队列清空时间。

**如何结合 Axiom 回答**

【当前已实现】Supervisor 可表达本进程活动 Run，Trace/RunMetrics 能看到每 Run 的模型、工具、步骤和延迟。

**当前没有实现什么**

【当前部分支持】项目没有 500 QPS 生产压测或多实例容量结论。

**如果继续扩展会怎么做**

【未来设计】建立真实任务分布的负载测试，Worker 上报可用 slot，由准入层按安全容量发放任务，并按队列年龄扩容。

**面试官可能继续追问**

- **为什么不是 1000 个线程？** 大量时间是异步等待，线程不是并发请求的同义词。
- **实例数怎么算？** 总活动执行并发除以单实例安全并发，再加故障与峰值余量。
- **平均 2 秒能保证 P99 吗？** 不能，容量测试还要看尾延迟和突发分布。

### D2. 每秒 10 个长 Run、平均 60 秒，会发生什么？

**题目**

Agent 到达率只有每秒 10 个，但每个 Run 平均 60 秒，系统压力大吗？

**先给结论**

大约会同时存在 `10 × 60 = 600` 个 Run。Agent 系统即使 QPS 看起来不高，也可能因为任务持续时间很长产生很高的生命周期并发；真正压力来自活动 Task、内存、模型/Tool 并发和持久化写入。

**完整回答**

我会把 600 再分成正在执行、等待 LLM、等待 Tool、等待 Child 和等待人工批准。等待批准的 Run 可以只保留持久状态，不应持续占 Worker、数据库连接或容器；正在调用模型和工具的部分才消耗稀缺并发 slot。

然后估每个 Run 的消息、Context、Trace 和工作区内存，平均有几次 LLM/Tool 调用，每一步写多少 Checkpoint。如果每个 Run 平均 8 次模型调用，10 个新 Run/s 最终可能对应约 80 次模型调用/s，而不是 10。Child Run 并发还会形成短时尖峰。

**排查 / 设计步骤**

1. 用到达率和生命周期估算同时存在的 Run。
2. 按 RUNNING、WAITING 和 approval 状态拆分。
3. 估每 Run 内存、磁盘、LLM/Tool 调用和写入。
4. 让等待态释放活动执行资源。
5. 用有界队列和配额控制 active slice。

**如何结合 Axiom 回答**

【当前已实现】Checkpoint 有 WAITING_APPROVAL/WAITING_CHILD 等状态；RunBudget wall time 跨等待和重启；Supervisor 只登记当前进程正在执行的 Task。

**当前没有实现什么**

【当前部分支持】没有面向 600 个共享 Run 的 parked-run scheduler、自动恢复队列和工作区生命周期管理。

**如果继续扩展会怎么做**

【未来设计】等待态只留共享数据库记录，需要继续时重新进入持久队列；调度器按 LLM、Tool、内存和 tenant slot 激活 Run。

**面试官可能继续追问**

- **等待 HITL 是否算 active？** 生命周期上算存在，但不应占活动 Worker slot。
- **为什么 QPS 低还会 429？** 一个 Run 会多次调用模型，Child 还可能并发调用。
- **最容易漏算什么？** Run 生命周期、每 Run 多步骤和等待状态占用。

### D3. 怎样估算 Worker 数量？

**题目**

生产化后需要多少 Agent Worker？

**先给结论**

不能只按 CPU 核数估。先用压测找出单 Worker 在目标 P99、错误率和内存水位下能安全执行多少 Run，再用峰值活动执行并发除以单 Worker 容量，并加入故障、发布和突发余量。

**完整回答**

Agent 多为 I/O 型，单 Worker 可以维护多个协程，但并发上限常由内存、LLM quota、Tool/MCP 和数据库决定。我要逐步提高并发，观察吞吐何时不再线性增长、P99 何时陡升，这个拐点以下才是安全区。交互任务和批任务最好分池，避免批量长任务抢光低延迟资源。

**排查 / 设计步骤**

1. 测单 Worker CPU、内存、事件循环和下游占用。
2. 逐步提高并发找到 P99 拐点。
3. 计算峰值 active concurrency。
4. 加单机故障和发布余量。
5. 按交互/批任务分池验证。

**如何结合 Axiom 回答**

【当前已实现】本地 Tool semaphore、Child 并发和 Supervisor active count 提供单进程维度。

**当前没有实现什么**

【当前部分支持】没有 Worker fleet、容量上报或自动扩缩容。

**如果继续扩展会怎么做**

【未来设计】Worker 上报活动 slot 与资源水位，调度器按能力分发；扩容同时受模型和 Tool 配额约束。

**面试官可能继续追问**

- **async 是否意味着无限并发？** 不是，协程、内存、连接和下游都有上限。
- **按 CPU 扩容够吗？** 不够，Agent 常由外部配额和内存先饱和。

### D4. LLM 配额怎样进入容量模型？

**题目**

怎样把模型 RPM、TPM 和并发限制纳入容量规划？

**先给结论**

要同时计算请求、Token 和并发三个维度。若每个 Run 平均 4 次模型调用、每次 5000 Token，10 Run/s 就约等于 40 次模型调用/s 和 20 万 Token/s，任何更低的 Provider 上限都会先成为瓶颈。

**完整回答**

实际设计不能只用平均值，还要看 P95 输入长度和输出长度，避免少量超大 Context 吃光 TPM。调用前按估算预留，请求结束后按实际 usage 结算；不同租户设置额度和优先级。若配额不足，可以排队、缩 Context、限制输出或路由，不能靠增加 Worker 解决。

**排查 / 设计步骤**

1. 统计每 Run 模型调用和 Token 分布。
2. 换算峰值 RPM、TPM 与同时调用数。
3. 对比 Provider 和账户配额。
4. 设计预留、实际结算与租户公平。
5. 监控 429、队列年龄和配额利用率。

**如何结合 Axiom 回答**

【当前已实现】BudgetManager 会预留模型调用和估算 Token，再用实际 usage 结算单棵 Run tree。

**当前没有实现什么**

【当前部分支持】它不是所有 Worker 共享的全局模型配额器。

**如果继续扩展会怎么做**

【未来设计】LLM Gateway 维护全局并发、RPM/TPM、租户配额和优先队列，permit 有过期时间防止 Worker 崩溃泄漏。

**面试官可能继续追问**

- **为什么增加 Worker 不能解决 429？** Provider 配额不随 Worker 数增加。
- **预估 Token 不准怎么办？** 保守预留，结束后按实际值结算并调整估算模型。

### D5. 怎样估内存、磁盘和工作区容量？

**题目**

长 Run 的内存和存储容量怎样规划？

**先给结论**

要分别估活动对象和持久数据：内存包括 Runtime 状态、消息、Tool 缓冲、Trace 和缓存；磁盘包括工作区、append-only Checkpoint、ToolExecution、索引和 artifact。应看 P95/P99 大小，而不是只看平均。

**完整回答**

先测一个空闲、普通和大任务 Run 的内存/磁盘分布，再乘活动/保留 Run 数。Context 压缩只减模型输入，不等于原始 Checkpoint 变小；append-only 状态和 Trace 需要保留、归档或压缩策略。每工作区要有磁盘配额与清理状态，不能任务结束就误删仍需审计的 artifact。

**排查 / 设计步骤**

1. 测普通与大 Run 的内存和持久数据分布。
2. 估活动、等待和保留数量。
3. 限制单 Tool 结果、workspace 和 artifact。
4. 定义 Checkpoint/Trace 保留与归档。
5. 在长期压测中观察 RSS、GC 和 IO。

**如何结合 Axiom 回答**

【当前已实现】模型侧有 Context hard limit 与大历史结果投影；SQLite Checkpoint 保留完整恢复状态。

**当前没有实现什么**

【当前部分支持】没有租户存储配额、对象存储或生产 retention policy。

**如果继续扩展会怎么做**

【未来设计】大结果存 artifact/object store，数据库只保存引用；对 workspace、Trace 和 Checkpoint 制定分级保留。

**面试官可能继续追问**

- **为什么不能只看 prompt 大小？** 原始执行证据、工作区和缓存仍占资源。
- **可以删除旧 Checkpoint 吗？** 可以设计安全压缩/归档，但要保留恢复、审计和当前状态需要的证据。

### D6. 当前 Axiom 流量增加 10 倍，什么先坏？

**题目**

本地/内部使用正常，流量突然增加 10 倍，你认为第一个瓶颈是什么？

**先给结论**

我不会机械回答数据库。第一步是量化 10 倍增加的是 Run 到达率、每 Run 步骤数、HTTP 查询，还是 Tool/LLM 调用；然后逐级压测，谁最先达到饱和，谁才是第一个瓶颈。

**完整回答**

LLM 配额可能先坏：Agent 一次请求会多次调用模型，出现 429 和模型排队。长 Run 并发可能先坏：到达率增加后活动 Task、消息和工作区占满内存。Tool/MCP 可能先坏：并发 Child 同时访问内部服务，Tool P99 和超时率上升。默认 SQLite 可能因单写者竞争先坏；配置 PostgreSQL 时，小型 pool 等待、热点 Run 行或数据库 IO 也可能先坏。backend 不同，证据也必须分别看。

确认信号分别是：429/配额利用率与 LLM 队列；活动 Run、RSS 和事件循环延迟；按 Tool 的并发、超时和连接等待；SQLite busy、事务和磁盘写延迟；连接池 acquire wait。临时先限制新 Run、降低 Child/Tool 并发、暂停批任务和问题依赖，不能先扩入口把流量更快压到下游。

长期按实际瓶颈演进：模型配额不足就做全局配额和路由；Run 太多就做准入、park waiting Run 和 Worker 池；SQLite 写竞争可切 PostgreSQL，PostgreSQL 则继续看 pool/SQL/热点；Tool 饱和则做隔离、缓存或扩下游。每次只改变主要瓶颈，并重测 P99、成功率和成本。

**排查 / 设计步骤**

1. 定义 10 倍的具体工作量和峰值持续时间。
2. 记录 Run lifetime、模型/Tool 次数和状态写放大。
3. 阶梯压测并同步看 429、RSS、Tool、SQLite 和池等待。
4. 找到第一个吞吐不升、P99 陡增的资源。
5. 先准入/背压止血，再优化或扩容并复测。

**如何结合 Axiom 回答**

【当前已实现】Supervisor、Tool semaphore、SQLite/PostgreSQL CAS、Budget 和 Trace 暴露了关键执行与存储边界，可用来建立基线。

**当前没有实现什么**

【当前部分支持】没有 10 倍生产压测、共享队列、全局限流、分布式 Worker 或水平扩展结论。

**如果继续扩展会怎么做**

【未来设计】先加有界准入与指标，再按证据选择 LLM Gateway、Worker pool、调整 storage backend/pool 或 Tool 隔离，避免一次引入整套平台。

**面试官可能继续追问**

- **最可能是哪一个？** 当前工作负载下 LLM 配额、长 Run 内存、Tool 并发和 SQLite 写竞争都合理，必须用指标确认。
- **为什么入口扩容可能有害？** 它会提高到达下游的速度，而下游容量没有增加。
- **先加 Redis 队列可以吗？** 队列能削峰但不能增加处理能力，必须有上限、过期和背压。
- **如何判断优化完成？** 目标负载下 P99、错误、成功率和资源水位都满足预期。

## 十一、场景题库：分布式演进（6 题）

### E1. 怎样把 Active Run Supervisor 扩展到多个 Runtime 进程？

**题目**

当前 Supervisor 只知道本进程任务，如果变成多台机器，某个 Run 到底归谁执行？

**先给结论**

我会把 Run 所有权写进共享数据库，而不是让每个进程各自认为自己是 owner。记录至少包含 run_id、worker_id、租约过期时间和递增版本；Worker 定期续租，只有持有当前版本的 Worker 才能推进状态。

**完整回答**

当前 `ActiveRunSupervisor` 保存 asyncio Task、所属 Event Loop 和线程，只能解决同一进程内的注册、取消和排空。多进程后，需要一个所有 Worker 都能看到的事实来源。一种做法是在共享数据库为 Run 原子写入 owner：没有有效 owner 或租约已经过期时，某个 Worker 才能 claim。

Worker 每隔几秒更新租约，表示自己仍活着。如果机器挂了，心跳停止，租约到期，其他 Worker 才能接管。这类机制通常叫租约（lease）和心跳（heartbeat）。但只有租约还不够：旧 Worker 可能网络隔离后恢复，因此每次 claim 还要递增一个 fencing token。之后所有 Checkpoint 写入都带这个版本，数据库拒绝旧版本，防止旧 Worker 继续写。

取消也要分两层：先把取消意图持久化到共享状态，当前 owner 轮询或收到通知后，再由本进程 Supervisor 调用 owner Event Loop 里的 Task cancel。这样现有 Supervisor 仍然有价值，只是它变成每个 Worker 内部的执行桥。

**排查 / 设计步骤**

1. 在共享库定义 owner、lease_expiry 和 fencing_version。
2. 用条件更新实现原子 claim、续租和释放。
3. 所有状态推进校验当前版本。
4. 持久化 cancel，再通知 owner 的本地 Supervisor。
5. 测试网络分区、暂停、双 claim 和旧 Worker 恢复。

**如何结合 Axiom 回答**

【当前已实现】进程内 Supervisor、Checkpoint sequence CAS 和 durable-first cancel 已实现，可继续作为单 Worker 内核。

**当前没有实现什么**

【当前部分支持】没有多进程 Run 所有权、租约、心跳、startup scanner 或递增 fencing token。

**如果继续扩展会怎么做**

【未来设计】在 PostgreSQL 增加 Run ownership 表或字段，使用原子条件更新；将所有权版本与 Checkpoint 更新绑定，并加入租约过期与冲突指标。

**面试官可能继续追问**

- **为什么 Supervisor registry 不放 Redis 就行？** 仅有临时 key 不能自动保证状态推进和 Checkpoint 写入使用同一 fencing 版本。
- **租约多久合适？** 要大于正常心跳抖动，又不能让故障接管等待太久，应依据网络和任务特性测量。
- **旧 Worker 恢复怎么办？** 递增令牌让共享存储拒绝它的旧版本写入。
- **CAS 和租约区别？** CAS 防过期状态覆盖；租约表达一段时间内谁有执行权，两者需要配合。

### E2. Worker 崩溃后，另一个 Worker 怎样接管？

**题目**

多 Worker 服务里，一台机器运行到一半挂了，怎样安全恢复 Run？

**先给结论**

新 Worker 不能立刻抢任务，要等旧租约失效，再通过原子更新拿到更高所有权版本。然后加载最新 Checkpoint、ToolExecution、预算和进展状态，重新构造 Runtime，从持久边界继续，而不是恢复原来的 Python 协程。

**完整回答**

流程可以概括为：租约到期，新 Worker CAS claim，得到新 fencing version，加载 Checkpoint，恢复 execution strategy、pending Tool index、Child 状态、预算和 ProgressDetector，再调用 resume。Trace 要关闭旧的 RUNNING Span并标记 recovered，让一次崩溃前后的证据仍可串联。

恢复前还要检查 Run 是否已经被取消或超过截止时间。遇到 ToolExecution SUCCEEDED 就复用；遇到 RUNNING 写 Tool 仍按副作用未知处理。Worker failover 解决“谁继续执行”，并不会消除外部 exactly-once 难题。

**排查 / 设计步骤**

1. 等租约过期并原子获取更高所有权版本。
2. 加载 Checkpoint、ToolExecution、预算和 Progress 状态。
3. 检查 cancel、deadline 和 parent/child 状态。
4. 按安全规则处理 pending Tool。
5. 恢复 Trace 并推进下一持久边界。

**如何结合 Axiom 回答**

【当前已实现】Checkpoint/CAS、stable Child ID、ToolExecution、预算/进展持久化和 `RunTracer.start_run(recovered=True)` 都可复用。

**当前没有实现什么**

【当前部分支持】当前支持从本地存储 resume，但没有自动跨 Worker 检测、claim 和调度。

**如果继续扩展会怎么做**

【未来设计】增加租约扫描器、原子接管、fencing、孤儿 Run 指标和人工死信处理。

**面试官可能继续追问**

- **为什么不能马上接管？** 旧 Worker 可能只是暂时网络抖动，立即接管会双执行。
- **能恢复 coroutine 吗？** 通常不能，恢复的是序列化状态和执行策略。
- **Tool 正在执行怎么办？** 读操作可按策略重试，写操作要查幂等或进入人工确认。

### E3. 为什么共享服务考虑 PostgreSQL？

**题目**

多实例架构里什么替代 SQLite，迁移要注意什么？

**先给结论**

PostgreSQL 是一个务实选择，因为多个进程能共享 durable state，并用事务和条件更新实现跨进程 Checkpoint CAS 与预算账本。Axiom 已实现这层 shared truth，但尚未实现 Run ownership；换数据库不会自动获得调度、隔离或防双执行能力。

**完整回答**

当前实现把 `runs` 作为最新 head，把 Checkpoint 映射为 `run_id + sequence` 历史；单条条件 UPDATE 推进 head，并在同一短事务追加 history。ToolExecution 以 invocation_id 唯一，预算 ledger 用 version 条件更新；Event 用 BIGINT identity 排序但允许 gap。长 Tool 执行期间不持有数据库事务，Trace/大 artifact 仍可独立存储。

迁移要有 schema 版本、双写校验或离线转换、备份恢复和回滚方案。连接池需要按全部 Worker 总量控制，不能每个实例都开满数据库上限。

**排查 / 设计步骤**

1. 映射 Run head、Checkpoint、ToolExecution、Event、预算和 control idempotency 约束。
2. 用条件更新保持版本冲突语义。
3. 设计 tenant/index/retention 与短事务。
4. 规划连接池、备份和迁移回滚。
5. 重跑崩溃、并发和恢复测试。

**如何结合 Axiom 回答**

【当前已实现】`RuntimeStore`、`EventRepository`、`ControlOperationStore` contract；SQLite 默认 backend；可选 psycopg 3/PostgreSQL backend；bounded pool、schema version、JSONB/TIMESTAMPTZ、原子 CAS、Event replay 和 ToolExecution 唯一约束。

**当前没有实现什么**

【当前部分支持】PostgreSQL backend 已实现，但首次任务环境没有可认证的 test DSN、Docker daemon 也未运行，因此真库 integration gate 尚未通过；没有 HA、在线跨 backend 数据迁移或自动 failover。

**如果继续扩展会怎么做**

【未来设计】真库 integration gate 通过后，再做 Durable Run Queue + Worker lease/heartbeat/fencing；不能用 advisory lock 偷换明确的 durable ownership 模型。

**面试官可能继续追问**

- **PostgreSQL 能避免热点吗？** 不能，热点 Run/ledger 行和长事务仍要设计。
- **为什么不先分库分表？** 500–1000 人的企业场景先把共享一致性和索引做对，分片应由真实容量驱动。

### E4. 怎样调度 1000 个长时间 Agent 任务？

**题目**

系统同时收到 1000 个长任务，你会如何调度？

**先给结论**

不会让 1000 个任务同时开始。先持久化任务并经过准入，有执行容量的任务获取 Worker 租约，其余进入有上限、有优先级、有过期时间的队列；等待 LLM、Child 或人工批准的 Run 应尽量释放活动 slot。

**完整回答**

调度器需要知道 Worker 可用并发、内存和 workspace 能力，也要知道租户配额、LLM/Tool slot 和任务优先级。交互请求可优先于离线评测，但要有公平性，避免一个租户长期饥饿。队列年龄比队列长度更能反映用户等待，过期任务不应继续执行。

Worker 拿到任务后写租约；完成、等待或失败时更新 durable state。重试不是简单重新投一条匿名消息，而是使用稳定 run_id 和幂等 claim。多次失败进入死信或人工处理。

**排查 / 设计步骤**

1. 量化到达率、生命周期和 active slice。
2. 定义租户配额、优先级和公平策略。
3. 建有界持久队列与过期时间。
4. Worker 按容量 claim/续租/释放。
5. 监控 queue age、failover 和死信。

**如何结合 Axiom 回答**

【当前已实现】本地 Plan/Multi-Agent 有 bounded scheduling，Run 状态和等待态可持久化。

**当前没有实现什么**

【当前部分支持】不是 1000 任务的 distributed scheduler，没有 durable admission queue。

**如果继续扩展会怎么做**

【未来设计】任务准入、优先队列、Worker lease、tenant quota 和队列驱动扩容分层实现。

**面试官可能继续追问**

- **为什么 waiting Run 要释放 slot？** 它暂时没有可执行工作，长期占 slot 会降低容量。
- **队列能解决过载吗？** 只能削峰，长期到达率大于处理率时仍必须限流或扩容。

### E5. 多用户工作区怎样隔离？

**题目**

500 名企业开发者共享 Coding Agent，文件和 Tool 权限怎样隔离？

**先给结论**

每个 tenant/Run 要有独立身份和工作区，在容器或等价沙箱中限制文件系统、网络、CPU、内存、磁盘和时间。Runtime 的 PermissionPolicy 是应用层授权，不能替代操作系统级隔离。

**完整回答**

调度时为 Run 创建独立 workspace，只挂载它允许访问的代码；Tool 执行同时校验 tenant identity、capability、路径和参数。Secrets 由短期凭证注入，不写入 Checkpoint、Trace 或日志。网络出口、symlink、子进程和 artifact 所有权都要测试。任务结束后按状态清理，失败和审计需要的 artifact 不能误删。

**排查 / 设计步骤**

1. 定义 tenant/Run 身份和授权范围。
2. 创建隔离 workspace 与资源配额。
3. Tool 同时做应用层权限校验。
4. 安全注入凭证并限制网络出口。
5. 审计、清理并测试逃逸边界。

**如何结合 Axiom 回答**

【当前已实现】DefaultPermissionPolicy、PathGuard、CommandGuard、ExecutionBackend 和 cwd 是应用层控制点。

**当前没有实现什么**

【当前部分支持】这些不是强多租户容器隔离，也不能保证阻止所有进程级逃逸。

**如果继续扩展会怎么做**

【未来设计】引入 sandbox/container、tenant IAM、secret broker、资源配额和 workspace lifecycle service。

**面试官可能继续追问**

- **路径检查够吗？** 不够，还要处理进程、网络、symlink 和内核级隔离。
- **日志能记录 Tool 参数吗？** 敏感参数应脱敏或只记录安全摘要和引用。

### E6. 多个 Worker 怎样共享 LLM 配额？

**题目**

所有 Worker 都调用同一个 LLM，怎样避免总量超过 Provider 限制？

**先给结论**

不能给每个 Worker 一份看似“全局”的上限，否则扩容后总流量按实例数增加。应该在共享的 LLM 网关或准入层维护全局并发、RPM/TPM、租户配额和优先级，Worker 调用前先获得 permit。

**完整回答**

请求前根据估算输入和输出预留 Token 与调用名额，完成后按实际 usage 结算。permit 要有过期时间，避免 Worker 崩溃后永久占额度。429 反馈可以动态降低发放速度。交互式任务优先，但要给其他租户最小份额，避免饥饿。

RunBudget 与全局配额是两层：前者防一棵 Run 无界消耗，后者防所有 Run 合起来压垮 Provider。两层都需要，不能互相替代。

**排查 / 设计步骤**

1. 按 Provider/模型维护全局请求、Token 和并发限制。
2. 加 tenant 配额、优先级和公平策略。
3. 调用前预留，结束后实际结算。
4. permit 设置 TTL 并处理 Worker 崩溃。
5. 用 429 和队列指标动态调整。

**如何结合 Axiom 回答**

【当前已实现】BudgetManager 的 reserve/reconcile、根 Run 聚合账本和真实重试计费可作为设计参考。

**当前没有实现什么**

【当前部分支持】当前预算只作用于单棵 Run tree，没有跨进程全局 semaphore 或租户配额。

**如果继续扩展会怎么做**

【未来设计】LLM Gateway 统一发 permit、排队、路由和结算，Worker 只持有短期调用资格。

**面试官可能继续追问**

- **为什么不是 Redis INCR 就够？** 还要处理并发 permit 生命周期、Token 预留/结算、TTL、公平性和失败恢复。
- **全局配额和 RunBudget 区别？** 一个保护共享供应商容量，一个限制单任务成本和工作量。

## 十二、这个项目需要 Nginx 或 Kubernetes 吗？

如果面试官问我，我的结论是：**对当前项目范围，不一定需要。** Axiom 当前最难的部分是长时间 Agent 执行，而不是公网流量转发。它真正要解决的是：进程崩溃后从哪里恢复，Tool 是否可能重复产生副作用，Context 怎样不爆，整棵 Run 怎样限制 Token 和成本，以及模型是否在原地循环。

Nginx 可以做反向代理、TLS、入口超时和负载均衡，Kubernetes 可以做容器调度、健康检查和副本扩缩容，但它们不会自动解决 Checkpoint、CAS、Context、RunBudget、Tool 幂等和无进展检测。即使把当前程序部署到十个 Pod，如果十个实例都不知道某个 Run 归谁执行，仍然可能重复执行；如果写 Tool 没有幂等协议，重启仍可能重复创建外部资源。

因此当前里程碑更值得把 Runtime 状态和证据链做扎实。为了简历“看起来像生产”而加入一套空壳 Kubernetes，不但增加维护成本，还容易被追问到镜像、资源限制、滚动升级、状态存储和任务接管时暴露边界不清。

如果产品真的变成 500–1000 名企业开发者共享，入口网关、负载均衡、共享数据库、任务准入、Worker 调度、租户隔离和自动扩缩容就会变得合理。此时 Kubernetes 可以承载 Worker 和沙箱生命周期，Nginx 或云网关可以管理入口，但选择仍应由 QPS、Run 生命周期、隔离和运维条件驱动。

面试时我会强调：架构演进不是补简历关键词，而是先确定工作负载和第一个饱和点，再选择最小可行组件。当前不实现 Nginx/Kubernetes 是范围选择，不代表不知道它们在共享服务中的位置。

## 十三、如果真的让我把 Axiom 生产化，我会怎么做？

我不会一步跳到“全分布式、多区域、Kubernetes 平台”，而会按风险逐层演进。每一阶段都要解决明确问题，并保留上一阶段验证过的 Runtime 不变量。

### Stage 1：单机生产加固

第一阶段仍然可以是一个 Runtime 实例，重点让它在可控负载下稳定运行。当前已具备分层超时、错误分类和安全重试；若真实负载暴露需要，再评估 LLM/MCP HTTP 连接复用、活动 Run/Child/Tool 并发限制、有界准入和 CPU、内存、事件循环、P99、429、Tool 超时、SQLite 写入与任务成功率告警。

这一阶段解决的是最常见的资源失控和排障困难，不需要改成分布式。Checkpoint、ToolExecution、Context、Budget、Progress 和 Trace 继续作为核心。

### Stage 2：企业共享服务

当多个开发者需要共享时，启用并先验证现有 PostgreSQL durable backend，再引入 Run ownership、Worker 心跳/fencing 和原子接管；入口增加有界持久队列、租户身份和配额；工作区放进受控沙箱；LLM 网关统一管理全局模型并发、RPM/TPM 和成本。

这一阶段解决多用户共享状态、Worker 故障接管、资源公平和安全隔离。这些都应由真实共享服务需求触发并独立验证；当前 feature-frozen Runtime 不预先实现 PostgreSQL lease、全局准入或跨 Run circuit breaker。

### Stage 3：更大规模

只有真实容量证明单个 Worker 池、单数据库或单区域成为瓶颈后，才做 Worker 水平扩展、分布式队列、基于队列年龄和资源水位的自动扩缩容、集中可观测平台和自动沙箱生命周期。向量检索是否独立集群、数据库是否分片，也应由索引规模和访问热点决定。

当前不值得实现完整 Kubernetes 平台、多区域、定制 API Gateway、服务网格、大规模向量库分片或自研自动扩缩容器，除非目标岗位明确是 AI Infra/平台工程。

## 十四、系统设计题的七步中文模板

### 第一步：先问清楚规模和目标

先问用户数、日均与峰值 QPS、请求是否交互式、数据规模、更新频率、延迟和可用性目标、是否多租户、是否有敏感数据。没有这些信息就直接画组件，通常是在猜题。

### 第二步：估算 QPS、延迟和并发

把日请求量换算成平均 QPS，但设计用峰值；用 `并发 ≈ QPS × 平均处理时间` 估 in-flight；再算每请求模型调用、Token、检索和数据库访问，找可能的硬配额。

### 第三步：画主链路

只画用户请求真正经过的关键组件，并说明哪些同步、哪些异步、哪些能并行。先让面试官看到你理解数据怎样流动，再讨论技术选型。

### 第四步：找可能的瓶颈

依次检查入口和队列、应用 CPU/内存、检索、数据库、连接池、LLM 配额和外部 Tool。不要机械说数据库，应该说明哪一个指标能证明瓶颈。

### 第五步：考虑故障和降级

为每个外部依赖设计超时、有限重试、熔断、隔离和降级。明确哪些功能可降级，哪些必须失败；写操作要处理幂等和不确定结果。

### 第六步：考虑一致性和恢复

说明任务状态存在哪里，Worker 崩溃怎样接管，旧 Worker 怎样被拒绝，缓存怎样失效，索引更新和权限怎样保持一致。Agent 场景还要解释 Tool 副作用和 Checkpoint。

### 第七步：补监控和容量规划

至少覆盖流量、错误、延迟和饱和度，并增加任务成功率、Token/成本、队列年龄、检索召回与降级比例。最后说明怎样负载测试、设置告警和逐步扩容。

## 十五、完整示例：设计一个日均 100 万查询的企业 RAG 系统

> **场景设计说明：以下是系统设计题的假设方案，不是当前 Axiom 已实现架构，也不是生产实测数据。**

### 1. 先明确工作负载

日均 100 万查询不是平均 100 万 QPS。一天 86400 秒，平均约 11.6 QPS。真正设计时必须问峰值、并发和延迟。为了继续讨论，我会明确做一个假设：工作日高峰约为平均的 8–10 倍，按峰值 100 QPS 设计；平均完整请求 3 秒，则约有 300 个请求同时存在。这个峰值只是面试估算，真实系统要用业务数据替换。

我还会问：文档有多少、每天更新多少、是否按部门/用户做权限过滤、目标是 300 毫秒首字还是 3 秒完整回答、答案是否必须引用来源、可用性目标是什么。企业 RAG 最容易被忽略的是权限：检索阶段必须先过滤用户无权看到的文档，不能检索后只在展示层隐藏。

### 2. 主请求链路

```text
用户 / IDE
    ↓
网关：认证、租户限流、请求 ID
    ↓
无状态 API 服务
    ↓
查询改写 + 权限过滤
    ↓
BM25 召回 ─┐
            ├→ 融合 → 小候选重排
向量召回 ──┘
    ↓
上下文去重、截断、引用构造
    ↓
LLM Gateway：配额、路由、熔断
    ↓
流式返回答案和来源
```

API 服务尽量无状态，便于水平扩展；会话、任务和审计状态放共享数据库。BM25 与向量召回相互独立，可以并行；融合后只对较小候选集重排，避免重排器成为瓶颈。Context Builder 在 Token 预算内去重，保留来源和权限标签。LLM 通过统一网关调用，以便控制全局并发、租户配额和备用模型。

### 3. 索引与数据更新

文档进入离线或准实时索引管道：解析、分块、权限标签、Embedding、倒排索引和向量索引。每个 chunk 带 tenant、文档版本和 ACL。更新采用版本化写入，索引成功后再切换可见版本；失败可重试但不让半更新内容对外。数据库保存文档元数据、版本和权限，原文可以放对象存储。

缓存分层设计：内容哈希到 Embedding 的缓存减少重复计算；文档缓存减少对象存储读取；检索缓存包含 tenant、ACL、index_version、query 和参数；稳定提示词前缀使用 Provider 支持的缓存。Redis 只是可能的实现，缓存键和失效语义比产品名更重要。

### 4. 容量和资源

峰值 100 QPS、3 秒平均响应约 300 in-flight，但检索、重排和 LLM 各自有不同并发。假设每请求一次 LLM、平均 4000 输入和 500 输出 Token，峰值约需要每秒 100 次调用、40 万输入 Token 和 5 万输出 Token；这只是估算，必须和 Provider 的 RPM/TPM/并发比较。

连接池按真实 DB duty cycle 设置，不能因为 300 in-flight 就建 300 个数据库连接。Worker 数由单实例在目标 P99 下的安全并发决定；队列只吸收短时突发，必须有上限和过期时间。扩容信号优先使用队列年龄、活动执行数和 CPU/内存，而不是只看 HTTP QPS。

### 5. 稳定性治理

每个依赖有剩余截止时间。模型 429 时，LLM 网关降低并发、按 Retry-After 有限重试，并将可等待请求留在有界队列；持续失败时熔断，按策略切小模型或明确失败。向量检索不可用时可以降级为 BM25-only，并在结果中标记召回能力下降。

Redis 不可用时可以绕过缓存访问源服务，但必须限流和合并热点请求，否则缓存故障会把数据库或检索集群打垮。一台 API Worker 崩溃时，无状态请求由负载均衡转到其他 Worker；若是长 Agent Run，则要等租约过期，由新 Worker 从共享 Checkpoint 接管。写 Tool 仍按幂等/未知副作用规则恢复。

### 6. 监控和质量

基础指标包括 QPS、错误、P50/P95/P99、队列长度与年龄、CPU、内存、连接池等待、检索/重排/LLM 分层延迟、429 和缓存命中。RAG 还要看 candidate recall、Recall@K、引用有效性、任务成功率、输入/输出 Token、成本和各降级路径比例。

发布时先跑离线回归，再小流量金丝雀；模型、提示词、索引或重排变更要带版本标签。HTTP 成功率正常但答案质量下降时，能通过版本、调用链和 Badcase 定位，而不是只看基础设施。

### 7. 如何联系 Axiom，而不夸大

【当前已实现】Axiom 的 Context、Budget、Trace、Evaluation、代码 hybrid retrieval、Checkpoint 和 ToolExecution 能复用为 Agent 执行与质量内核。

【当前部分支持】当前不是日均百万查询的共享 RAG 服务，没有上述网关、Redis 缓存、分布式检索集群、PostgreSQL ownership、全局模型配额和生产 SLO。

【未来设计】若需求真实出现，可以先把 Axiom Runtime 作为 Worker 内核，外层按 Stage 1–3 增加服务能力，而不是声称现有仓库已经承载该规模。

## 十六、这些东西和我的 Axiom 到底有什么关系

### 现在就强相关

超时、Tool 重试安全、异步并发、连接复用、模型限额、调用链定位、CPU/内存、Context 和 Budget 都直接影响当前本地 Runtime。原因是即使只有一个用户，一个长 Run 也会访问 LLM、MCP、文件和 SQLite，也可能超时、重复副作用、吃光 Context、内存或成本。这些知识能直接解释现有设计和后续小型加固。

### 面试要会，但现在不必实现

限流、背压、熔断、容量规划、水平扩展、共享数据库和分布式 Run ownership 是把单机 Runtime 产品化时必须会讨论的能力。但当前没有真实多租户流量，过早实现会引入大量运维和一致性复杂度，反而稀释项目在 durable Agent execution 上的证据。

### 现在可以保持浅层理解

多区域、大型 Kubernetes 平台、服务网格、全球分布式配额和大规模向量数据库分片，在当前目标下只需要知道解决什么问题、何时值得引入。除非面试岗位专门要求 AI Infra 或超大规模平台，不需要为了展示关键词完整实现。

## 十七、AI 应用工程落地 15 分钟速背

### 1. 线上故障

线上出问题，先判断“影响有多大”，再通过调用链找到“慢在哪一步”，最后用日志和资源指标确认“为什么慢”。先做限流、回滚、熔断或降级控制影响，再修根因并把 Badcase 变成回归用例。

```text
范围 → 指标 → 调用链 → 日志/资源 → 止血 → 复盘
```

### 2. 延迟优化

不要一上来加缓存或换数据库。先把入口、队列、检索、Context、LLM 首字、Tool、生成和持久化拆开，找到 P99 关键路径。优化后用相同并发复测 P50/P95/P99、错误率、成功率和成本。流式返回可能只让用户更早看到第一个字，并不一定缩短完整时间。

### 3. 稳定性

每个依赖都要有截止时间；只有短暂且幂等的失败才重试；重试要有次数上限、指数退避、随机抖动和总预算；依赖持续失败就熔断；一个慢 Tool 要有独立并发上限；入口不能让任务无限积压；系统过载时优先拒绝低价值和已过期工作。

### 4. 容量

每秒进入多少任务，还要乘每个任务在系统停留多久。500 QPS、平均 2 秒，大约有 1000 个请求同时存在；10 Run/s、平均 60 秒，大约有 600 个 Run 同时存在。请求并发不等于线程数，也不等于数据库连接数。

### 5. Agent 特有风险

一次用户请求会产生多次模型和 Tool 调用；等待批准的 Run 应持久化并释放执行资源；Context 变小不代表 durable state 变小；Run COMPLETED 不等于业务成功；写 Tool 超时不等于失败，恢复前必须判断外部副作用。

### 6. 分布式演进

当前 Supervisor 只知道本进程 Task。多 Worker 后，把 run_id、worker_id、租约过期时间和递增版本写进共享数据库；Worker 持续心跳，租约过期才允许接管；新 Worker 从 Checkpoint 恢复，旧 Worker 的写入由版本号拒绝。

### 7. 防夸大

我会说“当前是本地/企业内部 Runtime、SQLite、进程内 Supervisor”，不会说已经有分布式 scheduler、全局 quota 或多租户沙箱。我会说“已确认的 Tool 成功可以去重”，不会说所有外部副作用 exactly-once。我会把 PostgreSQL、队列、租约、网关和 Kubernetes 清楚标为未来设计。

## 十八、最值得背熟的 20 个答案

### 1. Agent 的完整执行链路是什么？

**60～120 秒口语答案：** 用户请求进入 Runtime 后先创建 Thread/Turn 对应的 Run，并写初始 Checkpoint。每一步模型调用前，ContextManager 会根据 Token 预算构造本次上下文；模型如果返回 Tool call，Runtime 先做权限判断和必要的 HITL，再用稳定 invocation_id 写 ToolExecution、执行工具并保存结果。之后结果回到模型继续推理，直到完成、失败、等待、取消或预算耗尽。整个过程受 RunBudget 和 ProgressDetector 控制，并通过 Trace/Span 留下证据。Plan 和 Multi-Agent 不是把所有状态塞在一个 Run 里，而是创建独立 Child Run，再由 Parent 持久化汇合。这样进程崩溃后恢复的是明确状态机，而不是重放整段提示词；已经确认成功的工具结果可以复用，未知副作用则保守等待确认。

### 2. Tool 频繁超时怎么查？

**60～120 秒口语答案：** 我先按 Tool 和依赖看影响范围，再从调用链拆出等待执行、连接池、建连、MCP Server、内部 API 和 DB。所有 Tool 都慢时查 Runtime 并发和公共网络；单个 Tool 慢就查它的下游。然后用固定小请求、直连服务或替代依赖做对照，确认是客户端排队、网络还是服务端慢查询。临时降低该 Tool 并发、熔断或暂停非关键调用，长期补分层超时、连接复用和每依赖隔离。超时不能自动重试写 Tool，因为外部副作用可能已经发生；还要确保超时后真正取消下游工作。

### 3. Agent 死循环怎样处理？

**60～120 秒口语答案：** 最大步骤数只能限制“最多做多少”，不能判断工作有没有进展。Axiom 用稳定证据检测重复相同 Tool、重复错误、A-B-A-B 短周期和状态长期不变。第一次触发时给模型一次有界恢复提示，要求换方法；继续重复才以 NO_PROGRESS 结束。检测状态写进 Checkpoint，所以重启不能把接近阈值的循环洗掉。面试中我还会强调阈值可能误报，因此要保守、允许一次恢复，并用 Badcase 调整。最终判断不能只看是否停止得更早，还要比较任务成功率、平均步骤、Token 和恢复后的有效进展。

### 4. Context management 怎样设计？

**60～120 秒口语答案：** Durable State 和模型 Context 必须分开。Checkpoint 是恢复与审计真相，Context 只是本次发给模型的有界投影。Axiom 每次模型调用前估算完整输入，超过水位就压缩旧前缀，同时保留当前目标、约束、最近消息和完整 Tool 协议；历史大 Tool 结果只在投影里截断，原始记录不删除。压缩后重新估算，仍超 hard limit 就在调用 Provider 前失败。质量证据分四层：结构/协议不变量、固定 10-case required-state retention、compression ratio，以及可确定任务上的 compressed-vs-uncompressed outcome probe。它仍不能证明开放域语义完全等价，也没有使用 LLM Judge。

### 5. Token 成本为什么突然上升？

**60～120 秒口语答案：** 我会拆模型调用次数、输入 Token、输出 Token、缓存 Token 和模型单价。输入上涨可能是检索 top-k、消息历史、Tool 输出或提示词变大；调用次数上涨可能是步骤、重试或 Child 增加；即使 Token 不变，换贵模型也会涨。Axiom 的预算账本会按 Provider 实际 usage 结算，并保留未知价格。排查时按模型、版本和 case 分桶，并查看 Context 压缩前后、缓存命中和 retry count。临时可以限制异常大 Context、停止失控重试或回滚模型配置。优化要同时看成功率和 Cost per Success，不能为少 Token 牺牲正确率。

### 6. API P99 突然上升怎么查？

**60～120 秒口语答案：** 我先比较 QPS、错误率和 P50/P95/P99，判断整体退化还是少数尾部请求。再从慢请求调用链拆队列、检索、Context、LLM、Tool 和 DB；最后用 CPU、内存、连接池、磁盘和依赖指标解释原因。P50 正常而 P99 高通常优先怀疑排队、慢依赖、锁竞争、重试或超大请求。止血可以回滚、降并发、暂停问题 Tool 或熔断，不能在不知道瓶颈时直接扩容。长期要给每层补分位数和版本标签，并用相同工作负载复测，确认不是把压力转移到另一个依赖。

### 7. P99 从 2 秒降到 300 毫秒怎么答？

**60～120 秒口语答案：** 我不会先承诺能做到，而会问 300 毫秒是首字、检索还是完整结果。假设 2 秒里 LLM 首字 900 毫秒、Tool 400 毫秒、检索和重排 450 毫秒，优化 20 毫秒数据库没有意义。检索占主导就并行 BM25/向量、缩候选；Tool 占主导就查连接复用、缓存和并发；队列占主导就做准入和 Worker 容量；LLM 占主导就减 Context、限输出或路由快模型。流式返回只改善感知延迟，最后用真实并发重测 P99 和成功率。如果完整 300 毫秒受 Provider 物理延迟限制，我会给出分阶段预算，而不是承诺无法验证的数字。

### 8. LLM 429 怎么处理？

**60～120 秒口语答案：** 先确认是请求、Token、并发还是账户额度限制。立即降低模型并发，把可等待任务放入有上限的队列；安全重试要遵守 Retry-After，使用指数退避、随机抖动、最大次数和总截止时间。持续 429 时熔断，暂停低优先级任务或切经过评测的备用模型。还要防止 SDK、Runtime 和网关重复重试造成乘法放大，并监控排队年龄而不是只看队列长度。Axiom 的 RunBudget 能限制单 Run 调用和 Token，但全局/租户 quota 仍是未来 LLM Gateway 的职责。

### 9. 为什么写操作不能无脑重试？

**60～120 秒口语答案：** 创建工单 API 可能已经在服务端成功，只是回包时网络断开，Agent 看到 timeout。直接重试会创建两次。安全方案是为一次逻辑操作使用稳定幂等键，下游重复收到时返回同一结果；或者超时后按操作 ID 查询状态；仍无法判断就人工确认。Axiom 用稳定 invocation_id、参数哈希和 ToolExecution 复用已确认成功结果，对 RUNNING 的非幂等写 Tool 保守等待批准，但外部 exactly-once 仍需下游配合。Checkpoint 只能证明本地走到哪里，不能替外部系统证明事务是否提交，这是回答时必须守住的边界。

### 10. 流量增加 10 倍，什么先坏？

**60～120 秒口语答案：** 不能机械说数据库。先问增加的是 Run 到达率、每 Run 步骤还是查询 API，再做阶梯压测。可能先出现 LLM 429，可能长 Run 把内存占满，可能 MCP/Tool 超时，也可能 SQLite 因 Checkpoint 和预算写入竞争。确认指标分别是模型配额、活动 Run/RSS、Tool P99、SQLite busy 和连接等待。先做有界准入和背压，再按第一个饱和点优化，不能只扩入口实例。每完成一次优化都要重新压测，因为瓶颈会移动；队列只能削峰，长期处理能力不足仍要扩真正受限的资源或降低工作量。

### 11. 容量怎样计算？

**60～120 秒口语答案：** 用 `并发量 ≈ QPS × 平均处理时间` 建立第一版估算。500 QPS、平均 2 秒，约有 1000 个请求同时存在。然后压测单实例在目标 P99 下的安全并发，计算实例数并加故障余量；再分别核对 LLM 请求/Token 配额、内存、Tool、DB duty cycle 和队列清空时间。并发请求不等于线程或连接数，最终数字必须由真实任务分布验证。对 Agent 还要另算生命周期并发：10 Run/s、60 秒平均生命周期就是约 600 个同时存在的 Run，其中等待态应释放活动执行资源。

### 12. 连接池怎样设置？

**60～120 秒口语答案：** 1000 个请求不等于 1000 个数据库连接，因为很多请求在等 LLM，只有一小段时间访问 DB。池太小会让请求等连接，池太大会让 DB 同时处理过多事务，造成 CPU、锁和上下文切换压力。我的做法是先缩短事务，观察活动/空闲连接、acquire wait、DB CPU/IO 和锁，从较小池开始压测到吞吐拐点；多实例还要算所有池相加后的总连接数。例如 20 个实例各开 50 个连接就是 1000 个，可能早已超过数据库安全容量，所以连接预算必须是全局的。

### 13. 内存持续增长怎么查？

**60～120 秒口语答案：** 我会把 RSS 与活动 Run、asyncio Task、消息、Tool 输出、Trace、缓存和句柄数对齐，比较任务结束后的对象快照。还要区分对象泄漏和 Python 分配器不归还 RSS。Context 压缩只减模型投影，不会删除 durable raw state。还要检查流式 HTTP/MCP session、文件和子进程是否关闭。临时降低并发和单任务大小，安全轮换 Worker；长期做每 Run 资源限制、artifact 外置、Trace retention 和长时间稳定性测试，并验证任务完成后对象数量能稳定。如果内存只随活动 Run 增长并在任务结束后稳定，就更像正常工作集而不是泄漏。

### 14. Worker 在 Tool 中崩溃怎么办？

**60～120 秒口语答案：** 恢复先读 Checkpoint 和 ToolExecution，核对稳定操作 ID 与参数哈希。SUCCEEDED 结果直接复用；RUNNING 的只读 Tool 可按策略重试，写 Tool 如果有幂等键或状态查询也能处理，否则进入人工确认。Axiom 已实现本地 crash dedupe 和不确定副作用路径，但没有通用 exactly-once。多 Worker 还要等待旧租约失效并使用 fencing token，避免旧 Worker 恢复后继续写。恢复的是持久状态机，不是原来的 coroutine；预算、进展和 Trace 也必须从原 Run 连续下去。最终副作用保证取决于 Runtime 和下游系统共同遵守幂等协议。

### 15. 错误率正常但任务成功率下降怎么办？

**60～120 秒口语答案：** HTTP 200 只代表服务返回，不代表答案正确。我要用相同数据集比较 baseline/candidate 的 trial success rate、required scorer、工具轨迹、步骤、Token 和成本，再从失败 Trace 看检索、Context、Tool 选择或模型行为。版本指纹帮助定位差异但不证明因果；确认 Badcase 后人工提升为回归用例。必要时即使错误率正常也要回滚。长期应把基础设施 SLO 和任务成功 SLO 分开，并为可验证任务建立完成契约，避免把模型自然语言里的“完成”当作正确性证据。Axiom 的 Run COMPLETED 也只表示执行正常终止，不等于业务目标已经验证。

### 16. Multi-Agent 资源竞争怎样控制？

**60～120 秒口语答案：** Child Run 不能各拿一份完整 Parent 预算，也不能无界并发。Axiom 为每个 Child 保留本地状态和 Progress，但所有后代用同一个 root budget ledger 聚合调用、Token 和成本；ToolExecutor 和策略并发也有上限。预算账本使用版本更新，避免并行 Child 同时拿走最后一份额度。生产化后还要把 Child 调度纳入全局 LLM/Tool quota，让一个 Parent 的 fan-out 不能占满所有 Worker，并区分等待 Child 与真正活动执行。如果一个 Child 卡住，应由 Parent 的依赖、review 和失败策略决定是否影响兄弟任务，而不是直接全部取消。

### 17. 分布式 Run 所有权怎样设计？

**60～120 秒口语答案：** 当前 Supervisor 只管理本进程 Task。多 Worker 后，在共享数据库记录 run_id、worker_id、租约过期时间和递增版本。Worker 原子 claim 后定期心跳；租约到期其他 Worker 才能接管。每次 Checkpoint 写都校验当前递增版本，旧 Worker 即使恢复也写不进去。这个机制通常叫 lease、heartbeat 和 fencing token。现有 Supervisor 仍负责 owner 进程内的 Task 取消与排空。取消操作也要先写共享 durable intent，再通知 owner，避免只取消本地 Task 却没有留下终态。租约表达的是有期限的执行权，不是持有期间永不失败的传统长锁。

### 18. Worker failover 的完整流程是什么？

**60～120 秒口语答案：** 旧 Worker 心跳停止，租约到期；新 Worker 用原子更新拿到更高所有权版本；加载最新 Checkpoint、ToolExecution、预算、Progress 和 Child 状态；检查取消与截止时间；重新构造 Runtime 后 resume。恢复的不是 Python coroutine，而是持久状态机。Tool SUCCEEDED 复用，RUNNING 写 Tool 保守处理，Trace 标记 recovered。Axiom 已有恢复内核，自动 claim 和共享 lease 属于未来架构。接管前不能只看数据库中写着 RUNNING，因为那可能是崩溃遗留；也不能刚丢一次心跳就抢任务，要容忍正常网络抖动。接管失败多次的 Run 应进入人工或死信处理，而不是无限循环。

### 19. 日均 100 万查询的企业 RAG 怎样设计？

**60～120 秒口语答案：** 日均 100 万平均只有约 11.6 QPS，设计要看峰值；例如假设峰值 100 QPS。入口做认证、租户限流，无状态 API 做查询改写和权限检查，BM25 与向量并行召回，融合后小候选重排，再做有 Token 预算的 Context，最后经 LLM Gateway 流式返回。缓存要带 tenant、ACL 和 index version；模型有全局 quota；向量挂了可 BM25-only，429 做退避/熔断，Redis 挂了绕源但限流。监控既看 P99，也看检索召回、答案成功和成本。文档索引要版本化更新，检索阶段就执行权限过滤，不能先检出敏感内容再在展示层隐藏。

### 20. 当前本地架构怎样演进成生产服务？

**60～120 秒口语答案：** 我会分三步。先做单机加固：超时、安全重试、连接复用、有界并发、准入和告警；第二步先把已实现的 PostgreSQL shared truth 通过真库 integration gate，再做 Run ownership/heartbeat/fencing、持久队列、租户沙箱和全局 LLM quota；真实规模继续增长后再做 Worker 水平扩展、自动扩缩容和集中观测。Checkpoint、ToolExecution、Context、Budget、Progress、Trace 和 Eval 都可复用。Nginx/Kubernetes 可以在后期承载入口和 Worker，但不会替代这些 Agent Runtime 核心语义。

### 21. 怎样把现有 Agent Runtime 接到 Agentic RL？

**60～120 秒口语答案：** 我先区分 Runtime 和 Trainer。Axiom 负责真实工具交互、权限、
Checkpoint、完成验证与可观察证据；每个 durable Run 是 episode，模型可见上下文是
observation，assistant/tool call 是 action，Tool 结果构成 transition。Run 终止后适配器从
现有证据生成 trajectory，不让 Runtime 再发一套 RL 事件；RewardPipeline 优先使用
CompletionVerifier 和确定性 scorer，再可选扣步骤、Token、成本和重试。Rollout 复用
Evaluation 的多 trial 执行，但保留独立训练数据生命周期和 split provenance。Agent
Lightning 1.0.1 适配器只完成了公开 `EventCreate` 边界的原生烟测；实际实验使用 TRL GRPO
+ LoRA。42 个 optimizer step 和参数 fingerprint 证明训练真实发生，但冻结 held-out 成功率
是 0/30 → 0/30，所以只能说工程闭环完成，不能说模型学会了更好的工具使用。

追问 GRPO 与 PPO 时，我会说明：PPO 用 clipped policy objective 并通常配 value/critic；GRPO
用同题多样本的组内相对 reward 构造优势，常可省独立 value model。它们都是外部 Trainer
能力。Axiom 的工程价值是高质量 episode、可验证 outcome reward、工具 transition 和安全
provenance，而不是重写优化算法。

这次负结果还说明 proxy reward 的风险：shaped reward 因更短的失败轨迹略有上升，但
outcome-only reward 和任务成功率完全没有变化。Agentic RL v1 因此冻结，不通过反复调参把
held-out 当优化目标；未来只有在非零基础能力、成功 SFT/curriculum 信号和严格 snapshot
隔离具备后，才重新评估 v2。

## 十九、七个高优先级补充场景

### 场景 A：远端副作用成功，但本地 ToolExecution 落盘失败

先把结果定义成 `UNKNOWN`，不能因为本地没有 `SUCCEEDED` 就断言远端失败。当前 Runtime 能用稳定 `invocation_id`、参数哈希和已持久化结果避免一部分重复执行；但本地 Checkpoint 与远端事务不是一个原子提交。生产方案应优先让下游接受同一幂等键，或提供按操作 ID 查询状态；两者都没有时进入人工确认或补偿流程。Checkpoint 解决本地恢复点，不提供跨系统 exactly-once。

### 场景 B：resume 与 cancel 同时到达

两个请求都应带幂等键，并从同一个最新 Checkpoint 做合法状态迁移。当前 SQLite/PostgreSQL sequence CAS 都会拒绝 stale write，控制操作也会校验请求哈希；如果 cancel 已提交更新版本，旧 resume 的 claim/后续 checkpoint 不能覆盖它，supervise 会重读并返回 `CANCELLED`。若 resume 已先合法完成，后到 cancel 会按终态规则冲突。生产多 Worker 还需要 ownership/fencing 约束谁能继续执行。

### 场景 C：两个 Worker 同时恢复同一个 Run

当前 PostgreSQL 让两个 Worker 看到同一 Run，Checkpoint CAS 只能阻止过期状态覆盖，ToolExecution 唯一约束只能阻止重复 durable row；两者都不能阻止两个 Worker 在 CAS 前调用外部 Tool。下一阶段应在共享数据库中原子 claim `run_id`，记录 owner、lease expiry 和递增 fencing token；租约过期后才允许接管，旧 Worker 即使恢复也不能继续提交。

### 场景 D：Parent 取消时 Child 正在执行写 Tool

当前实现先持久化 Parent `CANCELLED`，再 best-effort 取消仍非终态的 Child；已经完成的 Child 保留。如果进程恰好在两步之间崩溃，显式 Child resume/执行 preflight 会遍历 durable ancestors，发现已取消祖先后先把 Child 收敛为 `CANCELLED`，不会继续执行。当前仍没有后台 Recovery Scanner 主动扫尾；写 Tool 若在取消时已 in-flight，其外部结果保持 `UNKNOWN`，取消不等于补偿。

### 场景 E：成功率提高，但成本和延迟明显恶化

不能只看成功率宣告 candidate 胜出。先比较 trial success rate、P95/P99、Token、步骤和 Cost per Success，再按业务 SLO 设置硬门槛或 Pareto 取舍。当前 Evaluation 已能聚合成功率、Token、步骤、延迟、成本和每成功成本，并用 regression gate 拦截阈值退化；最终阈值仍需产品价值与容量预算共同确定。

### 场景 F：选对了 Tool，但参数错误

这应拆成 Tool Selection 与 Tool Argument 两个指标。当前 required/forbidden scorer 能判断“是否调用了该 Tool”，但 `EvaluationRunResult` 没有保留结构化参数，因此不能声称已实现参数准确率。生产评测应保存脱敏后的调用 schema、参数和预期约束，做字段级/语义级校验；运行时 schema 拒绝也应单独统计为 Invalid Tool Call Rate。

### 场景 G：多租户共享 Tool Runtime

当前 PathGuard、CommandGuard、能力策略、HITL、环境变量 allowlist、输出限制与超时终止提供应用层防线，但 Restricted backend 明确不是 OS sandbox，也没有租户级网络、CPU、内存、进程、文件系统和凭据隔离。生产方案应为每个租户或任务创建独立容器/微虚机与工作目录，采用默认拒绝的网络策略、短期凭据代理、资源 cgroup/配额和不可篡改审计，并用 tenant_id 贯穿队列、Checkpoint、Trace、artifact 与缓存键。
